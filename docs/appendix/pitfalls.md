# 迁移微信 3.x 数据时的坑（检查表）

### Pitfalls when writing into a live WeChat 3.x data directory

> 实测环境：WeChat **3.9.12.56**（x86），在 Windows 11 + WSL2 下操作
> 下面每一条都是我们**真的踩过**的。凡是当时没完全定位的，都标了 `推断`。
> 格式统一为 **症状 → 原因 → 做法**。
>
> **本篇是操作级**（写库时逐条对照）；**路线级**的错路与已证伪结论见
> [dead-ends.md](dead-ends.md)。**§0 是三条最该先记住的。**

---

## 0. 先记住三条

1. **任何写回之前，先跑 §13 的三道闸 + 强制备份。** 剩下的坑大多可以重来，丢掉客户端刚收到的
   真消息不能。
2. **凡是「边界」「页数」「路径分隔符」都不要写常量**，从数据里推导（§1、§3、§5）。
3. **`verify` 必须针对最终产物**，不是中间的明文副本（§11）。

| # | 一句话 |

## 1. 不要硬编码行边界

**症状。** 导入完成后：每个会话点进去**只显示几十条**消息（左侧会话列表的日期却是对的），
并且点「消息记录浏览（日期）」时**客户端卡死**。
Windows 事件日志给的是 `Application Hang`，**ID 1002**（不是 1000 `Application Error`），
**不产生 crash dump**。

**原因。** 我们的后处理脚本写死了 `localId <= <N0>` —— 那是当时**误以为**的最大值。
真实数据到 **<N1>**，中间 **数百行**整体被两道后处理漏掉：

| 偏离 | 行数 | 正确值（取自客户端自己写库的行） |
|---|---|---|
| `MSG.Sequence` 仍是每会话计数器（1..253） | 696 | `CreateTime * 1000`（**毫秒**） |
| `MSG.Reserved1` = 0 | 696 | 1（Type=34 语音为 2） |
| `MSG.BytesExtra` 仍指向 2.x 的绝对路径 | 44（Type=3） | `<ACCOUNT>\FileStorage\MsgAttach\...` |

这 696 行的 `CreateTime` 是会话里**最新**的，但按 `Sequence` 排序排到**最前** ——
按 `localId` 是「最后」、按 `Sequence` 是「最先」。客户端一个键走游标、另一个键找最新，
游标永远推不动 ⇒ 死循环。共涉及 **34 个会话**。

**做法。**

* 边界从数据推导：`select max(localId) from MSG`、`select distinct Type from MSG`，
  永远不要写字面量。
* 补完之后自查三条不变式：
  1. `Sequence` 是否等于 `CreateTime * 1000`（全库零例外才算过）；
  2. `Reserved1` 是否只有 1 和 2 两种取值；
  3. Type=3 的行，`BytesExtra` 子类型 3/4 是否都已指向 `FileStorage`。
* `Application Hang`（1002）**没有 dump** 可看，是本条最容易误判成「读崩」的地方；
  见到 1002 先怀疑死循环、怀疑排序自相矛盾。

## 2. 替换库前必须让客户端**干净退出**

**症状。** 替换主库、启动客户端后，**刚收到的那条新消息不见了**（没有报错、没有提示）。

**原因。** 客户端运行时 `MSG0.db` 旁边有**未检查点**的 `-wal`。我们实测在 WAL 里看到
**7 个帧**，涉及 `sqlite_sequence`、`Name2ID`、`MsgTalkerIdTypeSeqIndex(MSG)` ——
这就是「它刚插入了一条新消息」。直接换主库再删 `-wal`，等于把那批写入**静默回滚**。

**做法。**

* 走**托盘右键 → 退出微信**。干净退出时 SQLite 自己 checkpoint 并删掉 `-wal` / `-shm`。
* 替换前依次确认：① 进程消失；② **所有**目标库的 `-wal` 不存在或 0 字节；③ 再确认进程没复活。
  任一条不满足就放弃、**一个文件都不动**。
* 实测效果：这样保住了客户端在那次会话里刚收到的那条新消息（MSG 行数从 31,561 变到 31,562）。
* **反例**：用任务管理器强杀（或任何超时后 `kill -9`）会留下 `-wal`，而且**不会报错** ——
  「装完了，客户端也能开」不等于「没有丢数据」。

## 3. WCDB 会预分配：写回要按**头部页数**截断

**症状。** 写回的库大小正好等于预分配大小，但尾部页**已被加密** ——
这是客户端自己从不产生的形状。

**原因。** 3.9 / WCDB 会把 `MSG0.db` 预分配到固定大小（实测 **52,428,800 B** = 12,800 页；
分片滚动之后观测到 **62,914,560 B**），未使用的尾页是**原始零字节**。
而「无差别加密整个文件」会把那些零页也加密成合法的 SQLCipher 页。

**做法。**

* 写回前把明文截断到**头部记录的页数**：明文头 **bytes 28..32 是大端页数**
  （实测与 `pragma page_count` 一致）。截断后让客户端自己重新预分配。
* 功能上尾部零页本来就被忽略，所以不截断也能用；但保持「文件大小 == 头部页数」这一形状
  可以避免引入客户端从未产生的状态，出问题时也更容易二分。
* 文件大小不是完整性依据 —— 完整性看 **HMAC 逐页通过** + `pragma integrity_check = ok`。

## 4. 重新加密会换 IV：往返比对只能比**可用区**

**症状。** 往返自检报「所有页都不一致」，看起来像加密实现写错了。

**原因。** 重新加密时每页都生成**新的随机 IV**（`os.urandom(16)`），HMAC 也随之改变。
所以「解回来的页」和「原始明文页」**不可能**逐字节相同 —— 这是设计如此，不是 bug。

**做法。**

* 只比**可用区** `[0, PAGE - reserve)`（本版本 `PAGE = 4096`、`reserve = 48`）。
* 完整的 `verify` 应该是三件事一起过：
  1. 解密后**逐页 HMAC 通过**（计数：`n/n`）；
  2. 可用区往返比对**零页不一致**；
  3. 往返库 `pragma integrity_check = ok`。
* 只做其中一件都会漏（我们早期就吃过「HMAC 全过但内容其实是上一版」的亏，见 §11）。

## 5. WSL 下 `os.path.basename` 不认反斜杠

**症状。** 从客户端记录的 Windows 路径里取文件名，结果拿到**整条路径**。

**原因。** 在 Linux / WSL 下 `\` 不是路径分隔符：
`os.path.basename('a\\b\\c.jpg')` 返回整串，不会返回 `c.jpg`。

**做法。** 自己按两种分隔符切：

```python
import re
def basename(p: str) -> str:
    return re.split(r'[\\/]', p)[-1]
```

同样的道理：**不要**用 `os.path.join` 去拼客户端记的 Windows 路径再回写 ——
要么全程用 `\\` 手工拼字符串，要么全程按 POSIX 解析、只在写回时换回 `\\`。

## 6. 2.x 时代没下载过的附件，任何副本都不存在

**症状。** 一批十年前的文件附件在客户端里永远显示「已被清理」，怎么翻都找不到。

**原因。** 2.x 只在用户当年**点开 / 下载过**时，才把文件落到 `Attachment\`。
没下载过的，落盘这一步从未发生 —— 不是我们没找，是它从来没在这台机器上存在过。

**做法（以及一个警告）。**

* 接受它。186 条文件消息里 **54 条无法恢复**（实测确认）。
* 我们扫了 **9 个根、239,119 个文件**，只命中 **1 个同名而内容不同**的文件：
  库里记 **31,381 B** 的那个 `Desktop.zip`，实际候选是 4.1 MB / 77 KB / 14 MB 的现代文件。
  ⇒ **「同名」不等于「同一个文件」**；靠文件名跨目录凑数会把错误内容塞进历史记录，
  比缺文件更糟。匹配到的文件请先比大小（必要时比哈希）再决定。
  * 表情那次也踩到同一个坑：把搜索范围扩到 `AppData` 与程序安装目录后，确实搜到一个同名文件，
    但它只有 **46 字节**、开头是 ASCII `FileSize` —— 那是**一个第三方同步工具的占位桩**，
    不是真图，而且属于另一个微信号。⇒ **按文件名搜到的路径，必须先验大小 / 内容再采信**
    （另见 §17）。
* 反过来也有用：**先确认源文件存在，再改路径**。把路径写成一个不存在的文件，
  气泡会从「已被清理」变成「打不开」。

## 7. `MicroMsg.db` 有活 `-wal`：不要动它，但要管好 `ChatInfo` 锚点

**症状。** 替换 `MicroMsg.db` 之后会话列表、未读数或阅读位置异常；
或者某个会话**打开只显示几十条**。

**原因。** `MicroMsg.db` 旁边有**活 `-wal`**（实测数 MB 量级：我们观测到 4.6 MB，
另一阶段 2.4 MB —— 它会随客户端写入增长）。SQLCipher 的 WAL 帧是**加密**的，
而本工具链没有「加密 WAL 检查点」能力：只换主库再删 `-wal`，等于回滚客户端那批改动。

**做法。**

* **不要动 `MicroMsg.db`。** 需要改的会话元数据（下面这一条）单独 update，改完让它自己 checkpoint。
* 但必须保证每个会话的锚点成立：

  ```
  ChatInfo.LastReadedCreateTime  >=  max(MSG.Sequence)   -- 该会话
  ```

  单位是**毫秒值**（`Sequence` 那条时间轴），**不是秒**。
* 填错的后果和 §1 一模一样：阅读锚点落到 1970 年，那个会话打开**只显示几十条**。
  症状相同、原因不同，排查时两个都要看。

## 8. 把 `Start Time` 前移会让客户端滚出**新分片**

**症状。** 改完 `DBInfo` 的 `Start Time` 之后，`Msg\Multi\` 下凭空多出三个文件。

**原因。** `Start Time` 同时是「本分片的纪元」。把它挪到很早以前，
客户端会认为当前分片太老，于是为**新收到的消息**开一个新分片。

**实测。** 新增：

```
Msg\Multi\MSG1.db          52,428,800 B
Msg\Multi\MediaMSG1.db         20,480 B
Msg\Multi\FTSMSG1.db           73,728 B
```

**做法。**

* 这是**预期行为，不要试图消除它**：多分片是 3.9 的正常布局，客户端读所有分片。
  本次 `Start Time` 前移恰恰是语音能播放的关键（见 `../detail/voice-start-time.md`）。
* 工具必须按多分片写：
  1. 不假设只有 `MSG0.db`；
  2. 检查**所有** `*.db` 的 `-wal` 是否归零（第 2 条）；
  3. 媒体也要看对应分片（目录里同时出现了 `MSG1.db` 与 `MediaMSG1.db`，
     命名上是同前缀配对 —— `推断`，但按这个假设写不会错）。
* 反过来说：**改完 `Start Time` 之后，任何「只处理 MSG0.db」的脚本都要重新审一遍。**

## 9. 正则误伤：`length` 会匹配进 `voicelength`

**症状。** 只改了 `length="..."`，结果 `voicelength="..."` 的值也被改坏。

**原因。** `re.sub(r'length="[^"]*"', ...)` 会在 `voicelength="2415"` 里从 `length=` 开始匹配，
把语音时长改成一个错值。同类问题还有**锚点假设**：用 `rstrip().endswith('/>')` 判断
「XML 是不是以自闭合结尾」，在真实数据以 `</msg>` 结尾时会**静默不生效**（不报错，只是没改）。

**做法。**

* 用负向后顾限定词边界：

  ```python
  sc = re.sub(r'(?<![a-zA-Z])length="[^"]*"', 'length="%d"' % n, sc, count=1)
  ```

* 插入属性不要靠 `/>` 这种结尾假设，改成对确定存在的片段做替换，并 `count=1`。
* 改完**打印替换后的原文**（或重新 `parse` 一遍 XML / `BytesExtra`）核对结构，
  不要只看「函数返回了」。

## 10. 客户端会改写它自己拥有的东西

**症状。** 你昨天写进去的值，今天读回来变了；库文件大小也变了。

**原因。** 客户端会重写它自己产生的文件。实测它至少做了这几件事：

* 把 `MSG0.db` **重新预分配**到固定大小（我们写回的是截断后的 21 MB 左右，它自己会涨回去）；
* 给新会话补一行 `Name2ID`；
* 给**播放过**的语音行补一个 `BytesExtra` 子类型 5（`0a 04 08 05 10 01`）——
  全库里只有用户真的点过的那两行被改；
* 好消息：`DBInfo` 的 `Start Time` **没有**被改回去（跨会话保持）。

**做法。**

* 不要假设你的字节级写入会一直保持 —— **每次动手前先「快照 → 事后 diff」**：
  记录所有 `*.db` 的大小、mtime、`-wal` 大小与各表行数（以及小表的行内容哈希）。
  这是唯一能区分「客户端改的」和「我改的」的办法，也是这次能定位语音问题的关键手段。
* 备份永远不嫌多：每次写回前把被替换的库按时间戳存一份，并把**还原命令**打印出来。

## 11. 构建流程里重新解密会冲掉你刚打的补丁

**症状。** `build` 明明打了补丁，装进去的却是**没打补丁**的库；直到 `verify` 才报出来。

**原因。** 构建函数里又调用了一次「解密已安装库 → 覆盖工作副本」的读库函数，
把内存里刚改好的明文覆盖回原样。它不报错 —— 因为它「成功读到了文件」。

**做法。**

* **解密一次**，之后只操作内存 / 那份明文副本；读库函数加一个显式的 `refresh` 参数，
  默认不重新解密。
* `verify` 必须**解密最终产物**（要装进去的那个加密文件）回来逐项核对，
  不能只核对中间明文 —— 否则「构建」和「验证」看的是两个不同的东西。

## 12. `sqlite3` 的 `total_changes` 是连接级累计

**症状。** 日志写「删除 11 行」，实际只删了 6 行。

**原因。** Python `sqlite3` 的 `Connection.total_changes` 统计的是**这条连接上累计的**
受影响行数，包含之前所有 `UPDATE` / `DELETE`。

**做法。** 要打印单条语句影响的行数，用 `cursor.rowcount`；
或者在同一条语句前后各取一次 `total_changes` 相减。日志里的数字会被人当真，别让它说谎。

## 13. 写回前的三道闸 + 强制备份

**顺序不能换。** 前两道保证「不丢客户端的写入」，第三道保证「不撞上一个刚启动的客户端」
（它可能在闸 1 通过之后又起来），最后一道保证「万一还是坏了，能退回去」。

1. **闸 1 —— 客户端不在。** 而且要**连续几轮**确认。实测踩过：用户退出后 **2 秒**又启动，
   只看一次的脚本会把「正在退出」或「刚起来」判成「已退出」。
2. **闸 2 —— 所有目标库的 `-wal` 不存在或 0 字节。** 强杀会留下未检查点的帧（§2）。
3. **闸 3 —— 再确认进程没复活。** 这一条能挡掉「闸 1 通过 → 客户端启动 → 你替换」的竞态。
4. **强制备份 + 打印还原命令。** 先复制原库到带时间戳的备份目录，再删 `-wal`/`-shm`，再替换。
5. **装完立刻核对**：解密装进去的库，确认页数、HMAC、`integrity_check`、关键表行数都对。

可直接抄的骨架（把 `<...>` 换成你的值；占位符含义见仓库 `CONTRIBUTING.md`）：

```bash
#!/usr/bin/env bash
# 等客户端干净退出 -> 确认所有目标库 -wal 归零 -> 备份 -> 替换
set -u
DB_LIST=("<MSG_DB>" "<MEDIA_DB>" "<MSG_DB_SHARD_N>")   # 所有会被替换的库，含每个分片
SYNTH_DIR="<WORK_DIR>/synth"                            # 新库所在目录
BACKUP_DIR="<WORK_DIR>/pre_install_$(date +%Y%m%d_%H%M%S)"
PWSH="<PWSH_PATH>"; CLIENT_PROC="<CLIENT_EXE_NAME>"

# 采样 3 次取最大值；空/非数字一律当作「还在跑」（避免探测打嗝造成误判）
count_client() {
  local best=0 v
  for _ in 1 2 3; do
    v=$("$PWSH" -NoProfile -Command \
        "(Get-Process -Name $CLIENT_PROC -ErrorAction SilentlyContinue | Measure-Object).Count" \
        2>/dev/null | tr -d '\r\n ')
    case "$v" in ''|*[!0-9]*) v=1 ;; esac
    [ "$v" -gt "$best" ] && best=$v
    sleep 0.5
  done
  echo "$best"
}

# 闸 1：连续 4 轮确认不在（约十几秒静默），别把「正在退出」当「已退出」
ok=0
while [ "$ok" -lt 4 ]; do
  [ "$(count_client)" = "0" ] && ok=$((ok + 1)) || ok=0
  sleep 1
done

# 闸 2：所有库的 -wal 必须不存在或 0 字节
for db in "${DB_LIST[@]}"; do
  if [ -f "$db-wal" ] && [ "$(stat -c%s "$db-wal")" != "0" ]; then
    echo "！！ $db-wal 未归零（可能被强杀），放弃，未改动任何文件"; exit 1
  fi
done

# 闸 3：再确认没复活
[ "$(count_client)" = "0" ] || { echo "客户端又起来了，放弃"; exit 1; }

# 备份 + 替换（打印还原命令）
mkdir -p "$BACKUP_DIR"
for db in "${DB_LIST[@]}"; do
  cp -p "$db" "$BACKUP_DIR/$(basename "$db")"
  rm -f "$db-wal" "$db-shm"
  cp -p "$SYNTH_DIR/$(basename "$db")" "$db"
  echo "已替换 $db"
  echo "  还原： cp -p \"$BACKUP_DIR/$(basename "$db")\" \"$db\""
done
echo "完成。现在可以启动客户端了。"
```

## 14. 预分配空白页的 HMAC 必然失败 —— 别据此判定"参数不对"

**症状。** 解密之后统计页 HMAC，发现有**几千页不通过**（我们这边是 12,800 页里的 7,648 页），
于是判定"参数不对"或者"产物不可信"。

**原因。** §3 说过 WCDB 会把库**预分配**到固定尺寸，尾部是**裸零空白页**。那些页不是合法密文，
HMAC 当然不通过 —— **这与参数是否正确毫无关系**。

**做法。** 把失败数**分成三段**报告，结论**只看第一段**：

```
HMAC : 头部内 0    预分配区 7648    合计 7648
```

| 段 | 含义 | 怎么判 |
|---|---|---|
| **头部页数之内** | 真正的数据页（头部 bytes 28..32 给出页数） | **只有这里非 0，才说明密钥可能不对** |
| 预分配区 | 超出头部页数的空白页 | 失败是**正常**的，写回时会被截断丢掉 |
| 合计 | 上面两项之和 | 仅供参考，**不要**拿它做判断 |

另外：万一"头部页数"这个值本身不可信（为 0，或大于文件总页数），要**保守处理** ——
把所有失败都算进头部内，宁可误报也不能放过一个真错的参数。（**实测确认**）

## 15. 保留段必须在「空壳」阶段写死 —— 内容建好后再改**必坏库**

**症状。** 想"从 DDL 现造一个 3.x 库"，于是把建表语句直接灌进一个空文件，再想办法把每页保留段
改成 48 —— 结果库立刻损坏：

```
Tree 3 page 3 cell 0: Offset 4091 out of range 3815..4044
Tree 10 page 79 cell 278: Offset 4048 out of range 832..4044
→ database disk image is malformed
```

**原因。** SQLite 核心**没有**设置"每页保留段"的 SQL 接口，它只会把那段字节写成 `0`。
而保留段大小是**每页可用区布局的一部分**：`可用区 = page_size - reserve`。库一旦有了内容，
每页末尾的单元指针数组位置就是按当时的可用区算好的；此时再去改 `bytes[20]`，
每页的指针数组会**整体错位 48 字节**，于是所有页都成了"越界"。

**做法。** **先造一个「1 页、0 表、保留段 48」的合法空壳**，让 SQLite 一开库就从页头读到 48，
之后建表、插行都会自然按 `4048 = 4096 - 48` 走。`scripts/wxcom` 的 `make_sqlite_shell()`
就是这个空壳的生成器，`wxrows.py` 用它起手 —— 所以「不依赖别人的模板库」这条是站得住的，
但机制不是"改一个字节"，而是"先立好壳"。

同理，如果拿到一个保留段是别的值（比如 0）的库，**不要**试图就地改成 48 ——
正确做法是新建空壳、把数据**读出来再写进去**。（**实测确认**，见 `../detail/sqlcipher-params.md` §6①）

## 16. 搬过来的库里可能留着**旧机器的绝对路径** —— 但本例里它**不是**转圈的原因

> ⚠️ **先看结论：这一条在本项目的 4.x 上已被证伪**（M1）。
> 保留它，是因为它是**跨机器搬库**的通用风险；但**不要**拿它去解释 4.x 的转圈 ——
> 4.x 转圈的真因是**表情**，见 §17。

**症状（理论上）。** 迁移成功、消息都在，但**少数**媒体显示成灰色方块 + 一直转圈，永远不结束。
点它也没用 —— 客户端会去下载，而当年的 CDN 早就没了。

**原因。** `BytesExtra` 的字段含义**随消息类型、也随外层字段变化**，里面确实存在形如
下面这样的值：

```
C:\Users\<用户>\Documents\WeChat Files\<旧账号目录>\Attachment\<hash>
```

**旧账号目录名在新机器上通常不存在**（本例里，旧目录名是一个早已不用的账号别名），
于是理论上客户端按这个字符串找不到文件 ⇒ 走下载 ⇒ 转圈。

**为什么我们当初会这么写（以及错在哪）。** 当初的判据是这条正则：

```python
re.compile(rb'<旧账号目录名>\\([A-Za-z0-9_]+)\\([^"\\\x00-\x1f]+)')
```

它有两个毛病：

* **只捕获两级** `(子目录, 文件名)` —— 而库里真实的值有三级以上，路径被**截断**了；
* 把 `BytesExtra.f3.s3`（封面缩略图）与 `.f3.s4`（封面原图）**混在一起算**。

于是得到的 **1,491 条引用 / 1,467 个唯一文件 / 666 有源 / 801 无源** 这套数字**作废**。
字段级重扫（`private/tools/wx4_stalepath_scan.py`，把 `BytesExtra` 按 `(外层字段, 子类型)` 逐字段拆开）
的正确口径是：**唯一路径串 4,692 / 有源 3,856 / 无源 836**，明细见 `../detail/4x-migration.md` §5.3。

**已证伪的部分（实测确认，否定结论）。** 我们拿 **4 张真实的 `Type=49` 链接卡片**
（1 张来自内置助手会话、3 张来自群）在 4.1 上实测：**全部正常渲染** ——
显示「标题 + 摘要 + 一个链接图标」，**根本不去加载封面图**。
⇒ 那些"陈旧绝对路径"指向的是**卡片封面**，而 4.1 压根不用它。
**所以"把旧目录按原样补回去"这条路不必走**（详见 `../detail/4x-migration.md` §5.2）。

**教训（仍然成立）。** 任何"跨机器搬库"的场景都要先问一句：
**库里的路径是相对的还是绝对的？** 相对路径搬过去还能用，绝对路径一定失效。
这与 §5 是同一类错误的两面 —— 都是在"看起来一样的路径字符串"上想当然。
但**更要紧的第二课**是：**症状相同不等于原因相同** —— 我们当时手里只有一个转圈现象，
而它其实来自完全另一类消息（§17）。

## 17. 4.x 表情转圈：**别把「等一会儿才出来」误判成「永远不出来」**

**症状。** 4.x 里某些 `Type=47` 表情显示成灰色方块 + 一直转圈；
**但在"转发"对话框里可能能预览到图** —— 这个差别是定位的关键。
看久了很容易以为它"坏账"了，其实它可能只是**还没到手**。

**原因（实测确认，M1）。** 4.1 渲染表情时查的是**缓存**：

```
<账号根>\cache\<YYYY-MM>\Emoticon\<前2位>\<小写32hex>
```

* **迁移基本不搬表情**：迁移前 683 个被消息引用的名字里，这个缓存只命中 **204** 个。
  缺的几乎全是 3.9 侧那种 `V1MMWX` 容器（3.9 侧文件的两种"出身"见 `../detail/media-layout.md` §3.5 / §5）。
* 客户端会**校验「内容 ↔ 文件名」**：内容不符的文件被**删掉**；`V1MMWX`（内层 md5 = 文件名）被**接受**。
* **缓存里没内容 = 转圈**；而内容**可以联网按指纹取回**（指纹就是消息里的 32 位 hex 名字）。

**坑在哪（实测确认，M1 晚）。** 我们一度把「转圈」判成"本地没有原件、4.x 也不去取，
属于无解"，又据此引申出"必须逐条转发触发一次"。**这两条都错了**：

* 转圈是 4.x 的**原生懒加载**行为 —— 用户对照观察：与本次迁移**毫无关系**的 **一批较新表情**
  也**同样先转圈、不到 1 秒就出来**。差别只在**延迟**（新表情 <1 秒，十年前的几秒到一分钟）。
* **打开会话、翻过去、等一会儿**，客户端就会**联网按指纹取回**，**不需要转发**。
  实测（M1）：279 个"既转圈又无本地源"的表情里**已回流 153 个（55%）**，
  **凡用户真正翻过的会话都是 100%**（一个十年前那批里的表情群 144/144、一个小群 4/4、
  一个校友群 2/2、另两个各 1/1），用户实测**基本 10 秒内**加载出来；
  剩下 126 个**全部在用户还没重新打开过的会话里**。
* 转发不是没用，但它只是**逼客户端立刻渲染这一条** = **加速**；
  当时 4 个样本 100% 成功只是**相关**，不是"转发才有效"。
* **同一个毛病的第三次发作：把「快照」当「能力上限」。** 我们一度按某一时刻的缓存快照
  统计出"一个十年前那批里的表情群只回流 1.4%"，差点又写成"这个会话取不回来"；实际只是
  **用户没翻到那一段**（名字集中在更早的一段，而用户只翻了较晚的一半）。
  等用户从头刷一遍，**144/144 = 100%**。⇒ 判据是「**翻过、等过之后会不会好**」，
  不是「现在磁盘上有没有」。

**做法。**

1. **别急着拷文件、更别逐条转发** —— 先**打开会话、翻过去、等一会儿**，看它自己回不回来。
2. 想加速可以**对那条消息做一次「逐条转发 / 发送」**（发到内置助手会话最省事），
   哪怕最终因为版权保护**失败**也没关系。
3. 若仍要离线预置，才走文件层：把 3.9 的 `FileStorage\CustomEmotion\<前2位>\<大写名字>` 拷成
   `cache\<当月>\Emoticon\<前2位>\<小写名字>`（只增不改；工具见 `private/tools/wx4_fix_stickers.py`）。
   取回 / 接受后客户端会**本地解码**该文件、**用它自己的容器重写**缓存文件
   （实测：`3964140A…` 24,011 B → 24,016 B；`CE76D3DE…` 44,073 B → 29,568 B），
   **之后气泡与转发预览都正常了**。

**边界（都实测过）。**

* **合并转发**无效 —— 它只打成一张聊天记录卡片、**不逐个渲染**表情。
  这恰好说明加载的触发点是**逐条渲染**，而不是某种批量动作。
* **不需要 4.x 的密钥、不需要动任何 `.db`** —— 这两条是**实测确认**。
* **需要网络**（**已基本确定**）：那批「本地无源」的文件在本地四处穷尽搜索后无处可寻，只能来自网络。
  **但走 CDN 还是 API 属于未验证**（需要抓包）。
* **按文件名搜到的路径，必须验证大小 / 内容，不能只看文件名。** 表情"本地无源"的穷尽搜索
  扩到 `AppData` 与程序安装目录后，搜到过一个同名文件 —— 那是**一个第三方同步工具的 46 字节
  占位桩**（开头 ASCII `FileSize`），属于另一个微信号，不是真图。
  ⇒ "本地不存在可派生原件"的结论**仍然成立，而且更硬**（同名匹配的同类坑见 §6）。
* **长期成功率未验证**：腾讯侧可能下架 / 清理老表情包；转发时出现的**版权保护**失败提示
  是个值得警惕的信号。要测就给一个会话**翻到底、等够时间**再统计。
* ⚠️ **`business\emoticon\Persist` 那条路是关着的**：往里放野文件会被客户端**删掉**
  （它是索引驱动的）。**渲染走 `cache\`，不是它。**
  （旧版本文档写过"表情走 4.x 的 `emoticon.db` 登记，光有文件不够" —— 这个**归因是错的**。）
* 被推翻的旧结论与"错在哪"，`../detail/4x-migration.md` §5.5.5 原样保留。

## 18. 自检里的「坏密钥检查」可能永远为真

**症状。** 解密脚本用**错误的密钥**跑，照样打印 `OK` 并写出一份垃圾"明文库"；
一直到后面 SQLite 打不开才发现不对。换句话说：那个"坏密钥"检查从来没生效过。

**原因。** 代码顺序是「先 `out[0:16] = b"SQLite format 3\0"`，再判断
`if out[0:16] != b"SQLite format 3\0": 报错`」—— 被检查的那 16 个字节**刚被自己写进去**，
判断恒为假。**实测确认**：这是本仓库 2.x 解密脚本里的真实缺陷，直到给
`wxdec.py` 加 `--selftest`（自造一份伪库、再用全零密钥试解密）才把它抓出来。

**做法。**

* 判据要落在**解密产物本身**，而不是我们回填的魔数：SQLite 头偏移 16..23 的签名
  （页大小 `10 00`、读写版本 `1 1`、载荷比 `64 32 32`）才是真的检验 ——
  这正是内存扫描找密钥时用的判据，它被真实数据验证过。
* **跳过第 20 字节**（每页保留字节数）：2.x 上是 `0x30`(=48)，但其它版本未必等于密文侧的
  reserve，硬校验会误杀正确密钥 —— 这里只告警。
* 一般规律：**给"只有失败才报错"的检查写一个故意触发它的用例**。否则你验的是
  "正常输入不报错"，而不是"异常输入会报错"。`--selftest` 的退出码约定见
  `CONTRIBUTING.md`（0 通过 / 1 失败 / 77 跳过）。
