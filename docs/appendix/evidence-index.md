# 证据索引：每条结论是怎么来的、怎么自己验一遍

这个仓库里没有"据说"和"应该是"。每条技术结论都标注证据强度，并且尽量给出可自己复现的路径。

**证据强度的含义**

| 标签 | 含义 |
|---|---|
| **实测确认** | 我们在真机上跑过，有可重复的操作或可查的文件/日志作为依据 |
| **推断** | 现象一致、机制自洽，但没有直接验证机制本身 |
| **未验证** | 只是方案或猜想，**不要当结论用** |

## 一、2.x 段

| 结论 | 强度 | 证据 / 怎么复现 |
|---|---|---|
| 「版本过低」的主因是自带升级器把程序文件替换掉了 | 实测确认 | `../detail/launch-and-version-gate.md`：程序目录旁的明文升级日志记录了 `replaced file count` 与目标版本号；停用升级器后即可登录 |
| **跑一次旧客户端会往程序目录里"加"模块**：与从未运行过的基准相比多 21 个文件、0 丢失、共有文件大小全一致、10 个关键哈希全一致（8 个带运行当日 mtime） | 实测确认（差异）/ 推断（归因于运行中的客户端或升级器） | `../detail/launch-and-version-gate.md` §1：两棵程序目录的全量 `路径+大小` 比对 + MD5 对照 |
| **越界时间戳会被文件系统夹到自己的值域端点**：`1901-12-13` 与 `2446-05-10` 恰好是 ext4 可表示区间的两端；同一批值在 NTFS 上被夹成 `0`(1970) | 实测确认（值=ext4 端点、卷为 ext4、跨 FS 对照）| `../detail/launch-and-version-gate.md` §1 末尾：结论是**做忠实备份前必须先确认落地文件系统的时间戳值域** |
| 32 位客户端在 64 位系统上会被误判为版本过低 | 实测确认 | `../detail/launch-and-version-gate.md`：加兼容层环境变量后即可通过；社区两个独立项目做法一致 |
| 服务器下发 `MinVersion`，客户端持久化后把自己踢下线 | 实测确认 | `../detail/launch-and-version-gate.md`：明文 `.err` 日志里的返回码与查询间隔；删标记/看门狗可绕过 |
| 新设备豁免对 `(账号, 设备)` **只能成功一次** | 实测支持，机制未知 | `../detail/launch-and-version-gate.md` §7：同一台机器同一客户端，**换另一个账号**扫码会正常弹「新设备，等待 5 秒确认」；原账号此后每次都返回同一个失败码 |

## 二、3.x 解析参数

| 结论 | 强度 | 证据 / 怎么复现 |
|---|---|---|
| 页 4096 / 每页保留 48（IV16 + HMAC-SHA1 20 + pad12）/ PBKDF2-HMAC-SHA1 64000 / 每页 AES-256-CBC | 实测确认 | `../detail/sqlcipher-params.md`；`scripts/wxdec3x.py verify` 会做**全页 HMAC 计数**与 `pragma integrity_check` |
| `mac_salt = salt XOR 0x3A`，`mac_key = PBKDF2(aes_key, mac_salt, 2, 32)`，HMAC 覆盖 `ct‖IV‖le32(pgno+1)` | 实测确认 | 同上；`scripts/wxcom/` 里是参考实现 |
| **3.x 的 page-1 明文头是 `10 00 02 02`（WAL）**，2.x 是 `10 00 01 01` | 实测确认 | `../detail/sqlcipher-params.md`；用 `01 01` 当判据会**整代漏扫**（我们真的白跑过一轮） |
| WCDB 会把消息库预分配到固定大小，尾部是裸零松弛页，写回要按**头部页数**截断 | 实测确认 | `pitfalls.md`；`scripts/wxcom/truncate_to_header` |
| 重加密必然换 IV ⇒ 往返比对只能比**可用区** `[0, PAGE-reserve)` | 实测确认 | `../detail/sqlcipher-params.md`；`wxdec3x.py verify` 就是按可用区比的 |

## 三、2.x → 3.x 的行语义与媒体

| 结论 | 强度 | 证据 / 怎么复现 |
|---|---|---|
| `Sequence = CreateTime * 1000`（毫秒），不是每会话计数器 | 实测确认 | `../detail/row-mapping.md`；`scripts/wxrows.py verify` 会逐行核对全库一致性。反面症状见下行 |
| `Sequence` 写错会让**每个会话只显示几十条 + 日期轴卡死**（Windows 事件 **1002 Hang**，无 dump） | 实测确认 + 反例 | `pitfalls.md`：同一个库，改对 `Sequence` 后症状消失 |
| `MSG.TalkerId` 必须等于该 `StrTalker` 在 `Name2ID` 里的 `rowid` | 实测确认 | `../detail/row-mapping.md`；`wxrows.py verify` 会在有孤儿行时报错退出（我们实测零不匹配） |
| `MsgSequence` 是每会话计数器；`MsgServerSeq = 1`；语音行 `Reserved1 = 2` | 实测确认 | `../detail/row-mapping.md`；来源是**客户端自己写的行** |
| 列语义的正确来源是「让真客户端自己写一行，再读它的列值」 | 方法 | `../detail/row-mapping.md`：给出可操作步骤（用另一个账号发一条消息 → 快照 → 读新行） |
| 图片与缩略图是 **XOR 0xA0** | 实测确认 | `../detail/media-layout.md`：`5F 78 5F 40` ^ `A0` = JPEG 头 `FF D8 FF E0` |
| **视频目录是扁平的**（`Video\<name>`，没有月份子目录） | 实测确认 | `../detail/media-layout.md`：按这个猜测放好之后 91/91 全部可播（最初只是**推断**） |
| 表情文件名是客户端要去查的**键**。对**普通图片**源（GIF/PNG/JPEG），文件名 == **文件内容 md5**（实测 1/1；2.x 归档 `CustomEmotions/` 12/12）；对 `V1MMWX` 容器，文件名 == **内层原图**的 md5（4/4 不一致） | 实测确认 | `../detail/media-layout.md` §3.5 |
| 3.9 侧放**明文 GIF** 即可显示 —— 不强制 `V1MMWX` 容器 | 实测确认 | `../detail/media-layout.md` §3.5：动画表情显示正常 |
| 4.x 侧会**校验内容与文件名是否对应**：内容不符的文件被**删除**、`V1MMWX`（内层 md5 = 文件名）被**接受**并重写 | 实测确认 | `../detail/4x-migration.md` §5.5 |
| 客户端按**记录下来的路径**找媒体，**不按内容哈希** | 实测确认（**仅 3.9 侧**） | `../detail/media-layout.md`：四个内容完全相同的附件带着四个不同的 `BytesExtra` 子类型2 值 |
| 客户端按**记录下来的路径**找媒体，**不按内容哈希** | 实测确认 | `../detail/media-layout.md`：四个内容完全相同的附件带着四个不同的 `BytesExtra` 子类型2 值 |
| `BytesExtra` 是两层 protobuf：外层字段1 装 varint 类、外层字段3 装 bytes 类 | 实测确认 | `../detail/media-layout.md`；`scripts/wxcom` 里有编解码实现 |
| 字段顺序不影响播放 | 实测确认 | `../detail/voice-start-time.md` §4：把顺序重排成"客户端的样子"后行为不变 |

## 四、★ 语音与时间闸门

| 结论 | 强度 | 证据 / 怎么复现 |
|---|---|---|
| 语音**不在文件系统里**，在 `MediaMSG0.db` 的 `Media` 表一行一条（`Key = 2^40 + localId`、`Reserved0 = MsgSvrID`、`Buf` = 音频字节） | 实测确认 | `../detail/voice-start-time.md` §1；权威样板是**客户端自己写的那一行** |
| 往 `Msg/Media.db.MediaInfo` 里写数据**没有帮助**；3.9 建了这张表但从不写它 | 实测确认 | `../detail/voice-start-time.md` §2：整表清空后语音照样能播；且客户端收语音时快照显示该表始终 0 行 |
| 失败长相：气泡有时长、点了红感叹号或无限转圈、再点问「是否重新下载」 | 实测确认 | `../detail/voice-start-time.md` §3 |
| 音频字节、容器格式、`msgsource`、`MsgSvrID`、`MsgSequence`、会话、**有没有本地媒体** —— 全都不影响播放 | 实测确认 | `../detail/voice-start-time.md` §4：**8 条单变量对照**，每份副本只改一个字段 |
| 唯一影响播放的是**消息自己的时间** | 实测确认 | `../detail/voice-start-time.md` §4 最后一行：除时间外一个字节都没改的那份副本是哑的 |
| 闸门是 `DBInfo.'Start Time'`：`Sequence < StartTime` 的消息会被跳过本地媒体、直接走下载 | 推断（与 8 条对照全吻合） | `../detail/voice-start-time.md` §5；可复现：`scripts/wxstart.py check` 会直接判定"这些语音能不能播" |
| 把 `Start Time` 设早之后，语音全部可播，且客户端**跨会话不会改回去** | 实测确认 | `../detail/voice-start-time.md` §5；操作前后各做一次 `scripts/wxsync.py snap` + `diff` 即可确认它没被改写 |
| 副作用：客户端会滚出新分片 `MSG1.db` / `MediaMSG1.db` / `FTSMSG1.db` | 实测确认 | `pitfalls.md` / `../detail/voice-start-time.md` §5：改完之后数据根里多出这三个文件 |
| 客户端**成功播放**时只往那行补 `BytesExtra 子类型5 = 1`，不写任何媒体状态 | 实测确认 | `../detail/voice-start-time.md` §7：操作前后快照对比，`Media` 表一行未动 |

> **M1 更新**：本节原先整段标着「全部未验证」。官方**迁移**已在本机跑通并逐项验收，

>
> **M1 同日第二次更新**：「陈旧绝对路径 ⇒ 无限转圈」**已被证伪**；转圈的真因是 **`Type=47` 表情**，
> 而且修复是**纯文件层**的（**不需要访问 4.x 数据库、不需要动任何 `.db`**）。
>
> **M1 晚第三次更新**：又推翻两条 —— 「**4.x 不会去取**」和「**必须逐条转发触发**」。
> 正确的机制是「**懒加载取回**」：打开会话、等一会儿，客户端会**联网按指纹取回**。
> **需要网络已基本确定**（那批「本地无源」的文件本地四处穷尽搜索后无处可寻 ⇒ 只能来自网络），
> **但走 CDN 还是 API 仍未验证**（需要抓包）。
> 相关结论都并进了 5.1 的表里，被推翻的两条作为「已证伪」行保留。
>
> **M1 晚补充数据**：那批「既转圈、又无本地源」的表情共 **279** 个，
> 现已回流 **153 个（55%）**；**凡用户真正翻过的会话都是 100%**
>（一个十年前那批里的表情群 **144/144**，用户实测**基本 10 秒内**就加载出来）。
> 先前写的「一个十年前那批里的表情群只回流 1.4%」是**快照假象**，已作为「已证伪」行保留。

### 5.2 附件重复与精简（**已实测**）

> ⚠️ **本节是「只靠文件名」的那一轮**（迁移刚结束时、4.x 库还打不开时做的）。
> 它给的是**下界**，不是最终数字。**以 §5.4 为准** —— 那一轮能读库、也按内容哈希做了全树比对。
> 本节结论中「按文件名分组不安全」「必须哈希证实」这两条**仍然成立且已被 §5.4 再次证实**。

| 结论 | 强度 | 说明 |
|---|---|---|
| 4.x 按会话各存一份附件，重复命名文件数以千计 | 实测确认（计数） | `../detail/4x-migration.md` §3.1：整树 186,227 文件 / 222.61 GB，其中 `(N)` 后缀文件 **7,033 个 / 39.95 GB**，归入 4,070 个同基名组 |
| **按文件名分组去重是不安全的** —— 同基名组里确实存在内容不同的成员 | 实测确认 | `../detail/4x-migration.md` §3.1：2,800 个「≥2 成员」的组里，**886 个组（14.40 GB）的成员字节大小互不相同** ⇒ 必然是不同内容 |
| 安全去重**可回收 ≈ 19.87 GB**（下界），规则是只合并哈希证实全同的组 | 实测确认 | `../detail/4x-migration.md` §3.1：1,891/2,800 组为 `ALL_IDENTICAL`；886 个 `MIXED_BY_SIZE` 组未哈希 |
| 按文件名「顺手合并」会覆盖掉 **14.60 GB** 的不同内容 | 实测确认 | `../detail/4x-migration.md` §3.1：886 组（14.40 GB）成员大小不同 + 23 组（0.20 GB）等大但哈希全异 |
| 浪费按字节集中在少数大文件（>10 MiB 占 74.4%） | 实测确认 | `../detail/4x-migration.md` §3.1：≥1 MiB 的 3,222 个文件占 39.95 GB 的 97.6% ⇒ 去重要先按大小分桶 |
| 上述 19.87 GB **只是 `(N)` 命名形态那一部分**；跨会话同内容不同名要全树哈希才抓得到 | 未测量 | `../detail/4x-migration.md` §3.1 末尾：「本节没有测量的东西」 |
| 用 **NTFS 硬链接**折叠同内容文件 | 实测确认（**官方迁移本身就在这么做**）+ 建议 | `../detail/4x-migration.md` §3.3；删掉其中一个名字**不释放空间**（3.9 侧实测：0 字节回收） |
| 客户端按**记录下来的路径**找媒体，不按内容哈希 | 实测确认（**仅 3.9 侧**） | `../detail/media-layout.md`：四个内容完全相同的附件带着四个不同的子类型2 值。**原先写的"4.x 侧也是实测确认"作废** —— 它引用的证据就是"陈旧绝对路径 ⇒ 转圈"，而那条已证伪（见 §5.1） |

### 5.3 4.x 数据库层（**已打通**，M1）

> ⚠️ **本节在 M1 从「仍未验证」整体改写。** 旧版把"库打不开"当成事实，
> 并据此写了两条**已被推翻**的机制推断（见下表 ~~删除线~~ 行）。
> 公开侧只保留**结果与格式判据**；私有侧完整记录见 `private/references/`。

| 结论 | 强度 | 说明 |
|---|---|---|
| **每个 `.db` 有独立的 salt 与独立的 `enc_key`** | **实测确认** | 与 3.x 的"一个账号一把密钥"不同，这一条以前写错过 |
| SQLCipher 4 布局：AES-256-CBC / 页 4096 / **保留段 80**（IV 16 + HMAC-SHA512 64）/ **raw key（不经 PBKDF2）** | **实测确认** | 解密结果可被标准 `sqlite3` 直接打开 |

### 5.4 附件审计：重复与孤立（**已实测**）

> 全树口径：**189,921 个文件 / 208.17 GB**（快照时客户端在跑，是移动靶）。
> 方法、工具与完整产物见 [`../detail/attachments.md`](../detail/attachments.md)。

| 结论 | 强度 | 说明 |
|---|---|---|
| `hardlink.db` 的 `md5` 列**就是内容 md5**；`dir1`→月份 + `file_name` 能直接拼出物理路径 | **实测确认** | 抽 200 条，**(大小, md5) 200/200 逐字节吻合** |
| `msg/attach/**/Img/<32hex>*.dat` 的文件名是**图片 id**，**不是**本地那份（被重编码过的）明文的 md5 | **实测确认** | 从 `packed_info_data` 解出的 32hex **40/40** 能找到同名 `.dat`；而这些 `.dat` 解开后的内容 md5 与文件名**不符**（2/2） |
| 4.x 的 `.dat` 图片是**单字节 XOR 0xA0**；解出来就是完整 JPEG（`ff d8 ff e0` … `ff d9`） | **实测确认** | 抽 400 个样本，356 个直接命中；剩下 44 个是 `\x07\x08V2\x08\x07` 容器 |
| `message_content` 是 zstd（`WCDB_CT_message_content = 4`），解出来是 appmsg XML，含 `<title>` / `<md5>` / `<totallen>` | **实测确认** | 本机用 ctypes 调 `libzstd.so.1` 解开 **348,243** 条 |
| **判重必须按 inode 算**：客户端自己已经硬链接了一部分重复文件 | **实测确认** | 同一组 6 个 `.pptx` 共享一个 inode、`st_nlink=6` ⇒ 按文件数算会把可回收量**高估一倍**（35.98 GB → **24.22 GB**） |
| 全树重复：**9,533 组 / 17,269 个冗余文件**，按 inode 可回收 **24.22 GB**；其中 **2,576 组已全部硬链接**（可回收 = 0） | **实测确认** | `../detail/attachments.md` §4 |
| 跨封装（同内容、加密一份 + 明文一份）**极少**：只多出 9 组 | **实测确认** | 说明重复主要是「同一份东西被拷了很多遍」，而非「同一内容的不同封装」 |
| 有索引比例 **93.6%**（177,715 / 189,921） | **实测确认** | 判据三条：文件名 / 名前 32hex / 内容 md5（原始或解开容器后）任一命中 |
| 孤立文件按「有没有备份」分 A/B/C 三类，风险完全不同 | **实测确认** | A（有索引孪生）删掉绝对安全；C（完全独一份）必须人判断 |
| 抽样 **900 个孤立文件**，文件名与内容 md5 **全部 0 命中**库字节流 | **实测确认**（否定结论） | 三个区域各抽 300 个，逐条查库里的全部 32hex（155,524 个） |
| ~~`\x07\x08V2\x08\x07` 容器**格式未知**~~ | **已证伪** | 真结构：`[6B 魔数][4B aes_size][4B xor_size][1B flag][AES-128-ECB 图片头][明文中段][XOR 尾段]`。`15+align16(aes)+raw+xor == 文件大小` 在 **23,508/23,508** 上成立；**尾段密钥就是 `0xA0`**；单文件实测 `raw` 段原样 **100.00%** 合规于 JPEG 熵编码规则。上一版把它当成未知格式，错在**没去翻上游 zip** |
| V2 容器的时间分布：**十年前那批里 0 个**（绝大多数集中在最近一两年） | **实测确认** | ⇒ 与十年前那条恢复主线无关；总量 23,508 个 / 4.34 GB（全树 2.1%）。**它不是表情包** |
| `business/emoticon` 是**另一套**加密：`size % 16 == 0` 全部成立（603/603） | **实测确认** | 上游方案为 AES-128-CBC / IV=密钥、密钥 = `md5(seed+wxid+"EMOTICON")[:16]`、明文 `wxgf`；体量仅 52.6 MB |
| 4.x 的 `-wal` **无法靠 salt 判定当前世代**（帧头 salt 与 WAL 头部对不上，且低字节按 −1 递减） | **未验证** | 但实测主库与合并结果**行数、最大时间戳完全一致** ⇒ 合并无收益，本轮不合并 |
| **硬链接折叠已执行**：13,414 个文件 / 6,687 组折叠，释放 **24,585,990,237 字节（22.897 GB）** | **实测确认** | 路径条目 **0 变化**（189,187 不变）、路径条目总字节 **0 变化**；不同 inode 185,742 → 172,432。Windows 侧与 Linux 侧各独立验一遍，**0 异常 0 残留**。实际释放量与计划预期**逐字节相等** |
| **`st_ino` 不能跨平台比**：同一文件 drvfs 与 Windows 原生读出的 inode **恒定差 2**，`nlink` 一致 | **实测确认** | ⇒ 折叠工具只信自己现场 stat；plan 与 apply 必须同平台 |
| **「能省多少」必须按 inode 算**，按文件个数算会高估 | **实测确认** | 同一 inode 上的第 2、3 个名字折叠过来不省空间；本机 22.90 GB 会被算成 24.94 GB |
| **「同内容（`md5_norm`）」≠「同字节」**，跨封装重复**不可**硬链接 | **实测确认** | 明文 JPEG 与 XOR 加密的 `_W.dat` 归一化后同内容、落盘字节不同；硬链接会把加密容器换成明文 ⇒ 客户端解不出来。只折叠 `md5_raw` 相同者（本轮跳过 9 个） |
| **Windows READONLY 让 `os.replace` 报 WinError 5**，且失败残骸继承 keeper 的只读属性、`os.remove` 也失败 | **实测确认** | 381 个只读目标失败、其中 199 个留残骸被 `except OSError: pass` 静默吞掉 ⇒ 替换前只清**即将淘汰那个 inode** 的只读位 |
| **4.x 干净退出后 `-wal` 不会归零**（本机 82 个非零 / 80.5 MB，mtime 已冻结） | **实测确认** | ⇒ `AGENTS.md` 的「等 `-wal` 归零」在 4.x **做不到**，判据换成「进程消失 + `-wal` mtime 不再变」 |
| **放弃「改库删 `(N)` 名字」** | 决策（理由是外部依赖） | **微信的「手机→电脑聊天记录合并」必然以 PC 端已有文件名为输入**；篡改 `packed_info` 本地名等于给不可预测的组件喂非法输入。且它**不额外省一字节**，只影响 5,698 个名字（3.0%） |

## 六、流程与合规
