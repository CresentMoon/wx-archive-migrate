# 被投诉下架时的处理手册（以及不要做什么）

> 本手册是**工程与流程建议，不是法律意见**。
> 它记录的是「同类项目已经发生过什么」以及「在这种情况下怎样把损失控制在最小」。

> **结论速查**：① 这类项目**真的**被投诉过 —— 一次点名 30+ 仓库，**小仓库与 fork 都不豁免**（§1）；
> ② 被投诉时**不要 force-push**（§5/§6：它撤不回已公开的内容，还会毁掉自己排查的余地）；
> ③ 反通知**只对 DMCA 有效**，且要交出真实身份并接受美国联邦法院管辖（§2）；
> ④ **`.gitignore` 不是安全边界**（§7）。

---

## 1. 先摆事实：这类项目**真的**被投诉过

| 事实 | 来源 |
|---|---|
| 腾讯向 GitHub 提交 DMCA 投诉，**一次性点名 30 多个**「允许用户导出或分析自己聊天记录」的仓库 | [安全内参报道](https://www.secrss.com/index.php/articles/87234)、[新京报报道](https://m.bjnews.com.cn/detail/1769066718129127.html) |
| **小仓库不豁免**：「即便是规模较小、仅用于技术研究或个人数据整理的仓库，也在投诉名单中」 | 同上 |
| 腾讯的公开口径：这类项目「通过对微信客户端进行逆向工程等手段，**绕过客户端对本地数据文件的保护**」，并称「获得了平台支持，大部分项目也在平台沟通后**主动移除**违规内容」 | 同上 |
| **衍生仓库（fork）也被清理** | 同上 |
| 腾讯主张的法律依据包含 **DMCA §1201（未经授权规避技术保护措施）**，以及违反微信 ToS 中禁止逆向工程的约定、侵犯「存储格式、加密协议等知识产权」 | 同上 |
| 被点名的例子里包括 `wechat-clean` —— 一个**分析存储空间并清理**的工具，连导出功能都不算 | 同上 |

通知原文在 GitHub 自己的 DMCA 仓库里，是**公开且永久**的：

* 腾讯的一份通知（通知编号见 URL 里的日期）：<https://github.com/github/dmca/blob/master/2026/01/2026-01-08-tencent.md>
* 另一条同类记录：<https://github.com/github/dmca/blob/master/2026/09/2026-09-11-wechat.md>

**结论（工程上的，不是法律上的）**：这类仓库被投诉不是小概率事件，
而「删掉公开仓库」也不等于内容消失 —— 所以正确的准备方式是**假设它随时可能消失**。

## 2. 反通知（counter-notice）的真实边界

GitHub 有反通知通道，流程见官方文档：
<https://docs.github.com/en/site-policy/content-removal-policies/guide-to-submitting-a-dmca-counter-notice>

要点（**实测确认** = 文档明确写着，不是我们的经验）：

* 需要你的**真实身份与联系方式**；
* 需要**同意接受美国联邦法院的管辖，并同意接受对方的送达**；
* 需要在**伪证罪处罚**下声明「善意相信该内容是被误删或误认的」；
* 提交后 GitHub 一般会在 **10–14 个工作日**恢复内容，除非对方**起诉**；
* **它只对 DMCA 通知有效**。如果平台是按 ToS 或其它政策下架，**没有反通知通道**。

因此对**不在美国的个人开发者**，这条路的实际成本极高（时间、金钱、以及实名与管辖暴露）。

## 3. 实体论点（供参考，**不是**行动方案）

如果真要走抗辩，站得住的论点是这些：

* 访问的是**你自己账号、你自己设备、你自己数据**；
* DMCA §1201(f) 有「**为互操作性而逆向**」的例外（`Sega v. Accolade` / `Sony v. Connectix` 这条判例线）；
* 文件格式、字段语义、协议属于**功能性事实**，版权的保护很薄。

但必须清楚：**这些论点在平台的工单流程里几乎没有陈述机会** —— 平台不是法院，
它面对一份格式完整的通知时，最常见的处理就是先下架、再让你去和投诉方谈。

**所以不要把策略建立在「我们能辩赢」上，要建立在「删了也不丢」上。**

## 4. 真被投诉时该怎么做

1. **先分类**：被点到的内容里，哪些是「发不出去的」？
   二进制、反编译产物、他人数据 —— 这些**直接配合删除**，把事情结束掉。
2. **不要在现场争论**。平台流程不是辩论场；把精力留给「重新发布」。
3. **从本地 `git bundle` 在别的平台另建独立仓库**重新发布：
   * **不要用 GitHub fork** —— 衍生仓库会被一起清理；
   * 保留 `LICENSE` 与 `README`，这样镜像才是合法的再分发；
   * 顺手把这次被点到的内容从发布清单里去掉（见 §6）。
4. **接受一个事实**：公开仓库是「展示面」，不是「存档」。
   真正要保住的是你**自己的归档与迁移结果** —— 那些本来就在你自己的机器与 NAS 上。

---

## 5. 不要做

* **不要冒充身份**、不要用马甲账号规避流程 —— 这本身违反平台 ToS，而且会把个人风险放大。
* **不要试图规避有效的法律命令。**
* **不要把「技术上能不能抹掉」当成「应不应该抹掉」** —— 见 §6。

---

## 6. force-push 的真相

常见误解：「先把敏感内容提交了，出事再 `--force` 推一次就干净了。」

**`git push --force`（或 `--force-with-lease`）只是让远端分支上的旧 commit 变得不可达**，它：

* **不会删除对象** —— 旧对象仍在服务端，可以用已知 SHA 直接访问；
* **管不了 fork** —— 别人已经克隆/派生出去的副本你碰不到；
* **管不了引用** —— Events、PR ref、以及第三方归档（GH Archive、Software Heritage 之类）可能已经收录；
* **管不了已经立案的通知** —— 改写历史既**不撤销**通知，也**不改变** GitHub 侧那份公开记录。

你可以请 GitHub Support 跑一次 GC，但**清不掉别人已经克隆的副本**。

**对本项目尤其致命的一点**：那类**凭据是不可轮换的** ——
同一个账号重新登录会复现同一份（这正是"进过历史就洗不掉"的原因）。
**一旦进过 git 历史，就等于永久泄露，没有任何补救。**

> 所以唯一可靠的做法是**永不提交**。
> 仓库里的 `.githooks/pre-commit` 与 CI 跑的就是同一份
> [`scripts/check_no_secrets.sh`)../../scripts/check_no_secrets.sh)：
> 64 位十六进制串、账号标识、`wxid`、群 ID、个人绝对路径、手机号、二进制/凭据文件类型，
> 命中即**拒绝提交**。

## 7. `.gitignore` 的边界

`.gitignore` **只影响「未被跟踪」的文件**。它：

* ❌ **不能**让已经提交过的文件消失 —— 那要先 `git rm --cached` 再提交；
* ❌ **不能**清理已经进入历史的版本 —— 那要改写历史（而见 §6，改写也不彻底）；
* ✅ 只能防止**下一次**再把同类文件加进来。

所以「等出事了再往 `.gitignore` 里加一条」这个思路，只能防未来，防不了已经发生的事。
**正确顺序是反过来**：先把规则写进 `.gitignore` + `pre-commit` + CI，再开始写内容。

---

## 8. 一句话

**把公开仓库当成「随时可以没有」的东西，把归档和迁移结果当成必须保住的东西。**
上架前把发不出去的内容挡在门外（`check_no_secrets.sh`），下架时配合删除、从本地 bundle 另处重发。
