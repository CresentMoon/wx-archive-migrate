### 0.1 该验哪一段（**结论**，M1）

整条路线是**两段，性质完全不同**，验收责任也应不同：

| 段 | 谁在执行 | 该做到什么程度的验收 |
|---|---|---|
| **2.0 → 3.9** | **我们自己写的导入工具**（`sqlcipher-params.md` ～ `voice-start-time.md`） | **逐类型逐项**：文字 / 图片 / 语音 / 视频 / 表情 / 文件，每一类都要点开确认 |
| **3.9 → 4.1** | **腾讯自己的官方代码**（§2；我们只点了「加载」） | **结构性验收就够** —— 月份指纹、inode 命中、逐月对账、会话覆盖（§2.4 那 7 条判据），再加**浏览时抽样旁观** |

⇒ **不要替官方那一段做逐类型回归测试**：那既不在我们的责任面内，也不产生新信息。
实践中用户在浏览时已顺带覆盖：**图片、语音、卡片、文件均正常；视频未发现异常**（视频属抽样，非逐条）。

> 换句话说：**只有"我们自己搬的那一段"才需要按类型穷举验收**；
> 官方那一段的正确性由**结构对账**保证，而不是靠人肉点开每一条。

## 2. ★ 官方「加载历史聊天记录」—— 实测完整流程

本节是本文最有价值的部分：**整条 2.0 → 3.9 → 4.x 链路在 M1 真实跑通**，
下面是可复现的流程与验收方法。

### 2.1 触发点：**登录**，不是某个常驻菜单

这是最容易走弯路的地方。该功能**在登录时被唤醒**：

* 升级后首次登录会弹**「版本更新」**对话框，标题句是 **`加载版本更新前的聊天记录`**，
  按钮为 **`加载` / `不加载` / `暂不处理`**；
* 选择「暂不处理」后，**下次登录仍可再选**；
* 之后还能从**主窗口左下角的「≡」菜单 → `加载历史聊天记录`** 再次进入。

> **入口的确切位置**（**实测确认**）：主窗口左侧图标栏**最底部**有一个 `≡`（三条横线）。
> 点它展开的菜单依次是：
> `聊天文件` / `聊天记录管理` / **`加载历史聊天记录`** / `锁定` / `意见反馈` / `设置`。
>
> 注意图标栏**底部**这组图标（手机、`≡`）容易被忽略 —— 只扫上半部分会以为"没有设置入口"。

**不要混淆的三个不同流程**（UI 文案相近，做了完全不同的事）：

| 菜单项 | 做什么 |
|---|---|
| **加载历史聊天记录** | ★ 从**本机旧版微信目录**导入（本文的主角） |
| 从手机导入聊天记录 | 通过手机端把记录传到电脑（网络传输，与旧目录无关） |
| 迁移文件到新的存储位置 | 把 **4.x 自己**的数据根挪到别的盘（与旧版无关） |

### 2.2 前置条件与官方失败分支

迁移开始时会出现 **`授权访问原微信目录以导入聊天记录`** —— 要授权的目录是
**`...\Documents\WeChat Files`（上一层）**，**不是**里面的账号子目录。

从客户端自带的文案可以读出全部前置与失败分支（**实测确认**，取自程序内的字符串表）：

| 文案 | 含义 |
|---|---|
| `原微信客户端没有当前账号的聊天记录` | 在旧目录里**没认到当前账号** |
| `当前磁盘空间不足` / `导入最多需要 <N> 空间` | 目标盘空间不够 |
| `导入过程中你可以正常使用微信` | 导入**不阻塞**使用 |
| `退出微信会停止迁移` / `退出登录会停止迁移` / `重启微信会停止迁移` | **中途别退** |
| `已暂停加载聊天记录` | 是"可恢复的暂停"，**不是失败** |
| `由于部分文件无读写权限` → `未能加载之前版本的聊天记录`，`可重启电脑后再试` | 权限问题 |
| `由于部分文件已损坏` → `未能加载部分聊天记录` | 部分导入，不是全败 |
| `已导入的聊天记录仍会被保留在该微信客户端` | **源数据不会被删**（下方 §2.5 有实测佐证） |
| `后续将无法加载之前版本的聊天记录`（在选「不加载」时提示） | 一旦拒绝/清除旧目录，就没有第二次 |
| `存放聊天记录的云盘服务暂不可用` / `需确认云盘服务同步到本地后再试` | 旧目录若在**云盘同步范围**内会拦 |

### 2.3 迁移**实际做了什么**（实测确认）

三条结论，每条都有独立证据：

**① 大二进制走**NTFS 硬链接**，不是复制。**

原文字面就有 `边迁移边建立硬链接` / `迁移之后建立硬链接`。实测：
3.9 数据树里 **1,724 个文件 `nlink = 2`**，且这 1,724 个 inode
**在 4.x 里 1,724 / 1,724 全部命中**（遍历 4.x `msg\` 子树的 inode 表）。

用 `fsutil` 可以直接看到两个名字指向同一份数据：

```
> fsutil hardlink list "…\xwechat_files\…\msg\attach\<会话>\<YYYY-MM>\Img\<md5>_W.dat"
\Users\…\xwechat_files\…\msg\attach\<会话>\<YYYY-MM>\Img\<md5>_W.dat
\Users\…\WeChat Files\…\FileStorage\MsgAttach\<会话>\Image\<YYYY-MM>\<数字名>.dat
```

⇒ **磁盘上只有一份字节，两个路径。** 收益见 §2.6。

**② 增量合并：已存在的月份**相加**，不覆盖、不重复。**

在旧目录里**已经存在**的月份，迁移后文件数 = 原有 + 3.9 侧的对应数量。
实测两组（见 §2.6 表）完全吻合，且**没有产生任何 `(数字)` 后缀的重复文件**。

**③ 源数据是**只读**打开的。**

对照迁移前后的全量快照：
**消失 0 个、大小变化 0 个**，关键库 `sha256` 一字未变。
唯一的变化是**多出 18 个 `-shm` / `-wal` 边车文件**（其中 `-wal` 全是 **0 字节**）——
这是 SQLCipher 以 WAL 模式**只读打开**时必然产生的副产物，**没有任何写入**。

### 2.4 怎么自己验收（**指纹法**）

不要只看"会话列表里出现了老消息" —— 那可能是本来就有。用**迁移前不存在的东西**做指纹：

| 判据 | 做法 |
|---|---|
| **月份目录指纹** | 迁移前记下 `<4.x>\msg\migrate\{File,Video}\` 的月份集合；迁移后应**新增**旧目录里有、而 4.x 原先没有的那些月份 |
| **逐月对账** | 对每个新增月份比 `3.9 FileStorage\File\<月>` 与 `4.x msg\migrate\File\<月>` 的文件数（`Video` 同理） |
| **相加检验** | 对**两边都有**的月份，验证 `4.x迁移后 = 4.x迁移前 + 3.9` |
| **inode 命中率** | 迁移后统计旧树里 `nlink > 1` 的文件，逐个 inode 在 4.x 里找对应文件；命中率应为 **100%** |
| **会话×月份覆盖** | 比较两侧 `<会话>\<媒体子目录>\<月份>` 的组合集合，差集应为 0 |
| **零重复** | 统计 `(数字)` 后缀文件的 mtime，**不应出现当天的时间**。⚠️ 但**「有 `(N)` 后缀」本身不等于「迁移时重命名过」**：`msg\migrate\Video` 里两个账号实测都有大批 `(N)` 文件，而它们的 mtime **全部不在迁移当天**（是从源命名带过来的）。判据要落在 **mtime**，不是文件名 |
| **源未变** | 迁移前记 `sha256` 与文件数；迁移后重算 |

### 2.5 副作用与"别踩"清单

* **中途不要退出微信、不要退出登录、不要重启**（§2.2 有对应文案）。
* **源数据不会被删**，但也别指望它被清理 —— 想要回收空间得自己动手（§3）。
* 迁移会在**旧目录**里留下 `-shm` / `-wal` 边车文件（`-wal` 为 0 字节）。
  它们无害；旧客户端下次干净退出时会自行处理。
* **图片解码**、**表情库登记**、**`BytesExtra` 里的绝对路径** 这三件事迁移**不管**（§5）。
* 如果旧目录里有**同名的 `(数字)` 后缀文件**，那是原文件名的组成部分（很多中文文档本来就叫
  `xxx(1).pdf`），**不能**据此判断"迁移产生了重复"。

## 3. 附件重复问题（4.x 侧最实在的痛点）

> 本节内容**全部实测**，不是估计。整棵树 100% 走完、所有等大组 100% 做了 SHA-256，
> 无抽样（磁盘读 33.02 GB，耗时 283 s）。

### 3.1 现象

4.x 按**会话哈希**分目录存放附件（准确布局见 §4）。同一个文件如果出现在**多个会话**里，
就会在多个 `<会话哈希>` 目录下**各存一份**。另外文件名层面还有 `(1)` / `(1)(1)(1)`
这种重复命名。

| 项 | 实测值 |
|---|---|
| 整棵 `xwechat_files` | 24,575 目录 / **186,227 文件 / 222.61 GB** |
| 名字带 `(数字)` 后缀的文件（正则 `^(.+?)\((\d+)\)(\.[^.]*)?$`） | **7,033 个 / 39.95 GB** |
| 归入「同目录 + 同基名 + 同扩展名」的组 | 4,070 个（其中 1,270 个组只有自己、没有兄弟） |
| 组内成员 ≥2 个、可比较的组 | **2,800 个** |

### 分组结果：同名 ≠ 同内容

| 分类 | 组数 | 组内字节 |
|---|---|---|
| `ALL_IDENTICAL`（哈希全同） | 1,891 | 32.82 GB |
| `PARTIAL_IDENTICAL`（部分相同） | 0 | 0 |
| `ALL_DIFFERENT`（等大但哈希全异） | 23 | 0.20 GB |
| `MIXED_BY_SIZE`（成员大小就不同 ⇒ 必然不同内容） | **886** | **14.40 GB** |

**⚠️ 结论：按文件名分组合并会毁数据。**
886 个组的成员字节大小都不一样，一共 14.40 GB；另有 23 个组虽然等大，哈希也各不相同。
两者相加 **14.60 GB 的不同内容** —— 按文件名顺手合并，这些会被直接覆盖掉。

⇒ **去重只能由内容哈希驱动，绝不能由文件名驱动。**
正确规则：**只合并哈希证实为 `ALL_IDENTICAL` 的组。**

### 收益：≈ 19.87 GB（18.50 GiB），而且是**下界**

| 口径 | 可回收 |
|---|---|
| 只合并哈希证实全同的组（**安全**） | **19.87 GB / 18.50 GiB** |
| 若把 `MIXED_BY_SIZE` 组也按内容细分后合并 | 更多，但**未测量** |

### 浪费的分布：按字节看，是少数大文件

| 文件大小 | 文件数 | 字节 |
|---|---|---|
| < 64 KiB | 1,589 | 0.04 GB |
| 64 KiB – 1 MiB | 2,222 | 0.93 GB |
| 1 – 10 MiB | 2,310 | 9.26 GB |
| > 10 MiB | 912 | **29.72 GB** |

**1 MiB 以上**的 3,222 个文件占了 39.95 GB 里的 **97.6%**，其中 `> 10 MiB` 一档独占 **74.4%**。

**实践含义**：去重脚本**必须先按大小分桶**，只在等大的候选之间做哈希；
纯按文件哈希全树一遍要贵得多。

### 本节**没有**测量的东西

- **只在 `(N)` 这一种命名形态里测的。** §3 开头讲的"同一文件在多个会话目录各存一份"是
  **另一种**重复，文件名往往毫无关系 —— 那部分只能靠**全树内容哈希**才抓得到，本次没做。
  所以真实可回收量很可能显著高于 19.87 GB。
- 其他重复命名形态（`- Copy`、`副本` 之类）没有测。
- `MIXED_BY_SIZE` 组内**同大小成员之间**是否还有内容相同的，未哈希 ⇒ 未计入。
- 195 个文件同时落在多个组里（如 `X(1)(2).ext` 这种嵌套名）。

### 3.2 两条路共享的前提：为什么「让路径改指向精简后的文件」是安全的

**推断但依据充分**：

* **历史附件是只读的。** 正常使用中，用户是从微信里把文件「转存」到工作目录，
  而**不是**在数据根里就地改原文件。所以一条历史记录指向的文件，不会在改完之后又被谁重新写一遍。
* **历史消息不会再被回写。** 老消息在客户端眼里是终态，没有「稍后修正」的机制。
* **客户端按记录下来的路径找文件。** 这条在 3.9 上是**实测确认**（见 `media-layout.md`：
  四个内容完全相同的附件带着四个不同的子类型 2 值）。
  ⚠️ **原先写的"在 4.x 上也是实测确认"作废** —— 它引用的证据就是本文 §5.2 那个
  "陈旧的绝对路径导致无限转圈"，而那条**已被证伪**。所以这条**不要**再当作 4.x 侧的依据。
  （§5.5 另外显示：4.x 的表情是按**内容 md5 查缓存**的，本来就不走"记录下来的路径"。）

### 3.3 今天就能做：NTFS 硬链接（**零数据库风险**）

★ **注意：4.x 自己在迁移时就是这么干的**（§2.3）。所以这条路不是旁门左道，
而是与官方行为同构的做法。

* 不需要访问 4.x 数据库，不需要动任何 `.db`；
* 硬链接对客户端**完全透明**（它看到的还是普通文件）；
* 随时可以拆开。

**必须在微信完全退出后做**，并且**先 dry-run**：

```powershell
# 只处理媒体树；不要扫 db_storage（那里是数据库）
$root = '<DATA_ROOT>\msg'      # <DATA_ROOT> 例如 ...\xwechat_files\<账号>_<短hash>
$DoIt = $false                 # ← 先 $false 跑一遍，看清要动哪些文件，再改 $true
$Log  = "$env:USERPROFILE\hardlink_dedup_log.csv"

# 注意：Get-FileHash 的输出（FileHashInfo）只有 Path/Hash/Algorithm，**没有 Length** ——
# 要算省下多少空间必须回到文件系统去取大小，否则那一列恒为 0。
$groups = Get-ChildItem -LiteralPath $root -Recurse -File |
          Where-Object { $_.Length -gt 0 } |
          Get-FileHash -Algorithm SHA256 |
          Group-Object Hash |
          Where-Object { $_.Count -gt 1 }

$report = $groups | ForEach-Object {
    $keep = $_.Group[0].Path
    $len  = (Get-Item -LiteralPath $keep).Length
    [pscustomobject]@{
        Hash  = $_.Name
        Count = $_.Count
        Keep  = $keep
        BytesSaved = [int64]$len * ($_.Count - 1)
    }
}
$report | Sort-Object BytesSaved -Descending |
          Select-Object -First 40 Hash,Count,BytesSaved,Keep | Format-Table -AutoSize
'合计可省: {0:N2} GB' -f (($report | Measure-Object BytesSaved -Sum).Sum / 1GB)

if (-not $DoIt) { Write-Host 'DRY-RUN：把 $DoIt 改成 $true 才会真的建硬链接'; return }

# 安全替换：先把硬链接建在临时名上，成功之后才删原文件、改名就位。
# 这样 New-Item 失败时原文件**还在**（先 Remove 再 New 会在失败时丢文件）。
$done = @()
foreach ($g in $groups) {
    $keep = $g.Group[0].Path
    foreach ($dup in $g.Group[1..($g.Count - 1)]) {
        $tmp = "$($dup.Path).hl.tmp"
        try {
            New-Item -ItemType HardLink -Path $tmp -Target $keep -ErrorAction Stop | Out-Null
            Remove-Item -LiteralPath $dup.Path -Force -ErrorAction Stop
            Rename-Item -LiteralPath $tmp -NewName (Split-Path -Leaf $dup.Path) -ErrorAction Stop
            $done += [pscustomobject]@{ Removed=$dup.Path; Kept=$keep }
        } catch {
            Write-Warning "跳过 $($dup.Path)：$($_.Exception.Message)"
            if (Test-Path -LiteralPath $tmp) { Remove-Item -LiteralPath $tmp -Force }
        }
    }
}
$done | Export-Csv -LiteralPath $Log -NoTypeInformation -Encoding UTF8
"完成。动过的文件清单：$Log"
```

注意事项：

* 硬链接要求**同一个 NTFS 卷**。跨卷不适用。
* 如果客户端**原地修改**了其中一个文件，所有链接会一起变。历史附件是只读的，
  理论上不会发生；但**建议第一次只在一小部分目录上试**，观察一周。
* **删除某一个名字不释放空间** —— 只要还有另一个名字在，字节就是同一份。
  这一点与 3.9 侧的实测完全一致：删掉旧目录里那份，只减一个目录项，**0 字节回收**。
* 想回退：`fsutil hardlink list` 看清关系，删硬链接再从备份恢复。

### 3.4 解锁之后更彻底：改写库里的原始路径（**未验证**）

硬链接只折叠**数据块**，路径条目一个不少 —— 那些文件仍然要在目录树里各占一个位置。
真正把 N 条引用**收敛成一份文件**的手段，是改写数据库里记录的原始路径、再删掉重复副本。

比硬链接多出来的好处：

* **目录树变干净**，不再有 `(1)` / `(2)` / `(1)(1)(1)`；
* **不受「同一个 NTFS 卷」限制**；
* **可以顺带把陈旧副本挪去冷存储**，然后让库指向新位置。

操作顺序（**核心纪律：永远按内容哈希分组，绝不按文件名分组**）：

```text
1. 备份 4.x 数据根，并记下要改的库的哈希。
2. 按【内容哈希】给附件分组。同名不同内容是真实存在的 ——
   `报告.pdf` 与 `报告(1).pdf` 完全可能是两份毫不相干的文件。（§3.1 有实测数据：
   仅"字节大小不同"这一项就排除了 886 个组 / 14.40 GB。）
3. 每组只保留一份「规范文件」，把其余引用全部改写到它；
   输出【路径映射表】并留档（这是唯一的回退依据）。
4. 等映射生效、客户端能正常打开之后，才删多余的副本。
```

风险与边界（**未验证**）：

| 项 | 说明 |
|---|---|
| 前提 | 需要读库里的引用记录 —— 本项目**有意不做**这一步，理由见 [`guide-attachments.md`](../guide-attachments.md) |
| 风险 | 库里若另存了 MD5 / 大小等字段，必须与保留的那份**同内容**文件对得上 |
| 风险 | WCDB 会预分配数据库文件，写回必须按**头部页数截断**，否则可能损坏（3.x 上已踩过，见 `pitfalls.md` §13） |
| 风险 | 客户端**升级后可能重新拷贝**文件，让改写失效 |
| 风险 | **§5.3 的字段级重扫说明：库里的路径字段不一定是相对路径，也可能是绝对路径，而且含义随外层字段/子类型变化** —— 改写前必须先摸清形态 |

**因此顺序是：先做 §3.3（今天就能做、零风险、可逆），等 4.x 的库能读之后再用 §3.4 收尾。**

## 4. 4.x 的附件到底存在哪（**实测确认**）

这是 §3.4 和 §5 的地基。两侧的目录**嵌套顺序正好相反**，很容易看错：

| 消息类型 | 3.9 路径 | 4.x 路径 |
|---|---|---|
| 图片（原图/缩略图） | `FileStorage\MsgAttach\<会话md5>\Image\<YYYY-MM>\<数字名>.dat` | `msg\attach\<会话md5>\<YYYY-MM>\Img\<内容md5>_W.dat` |
| 文件附件 | `FileStorage\File\<YYYY-MM>\<原名>` | `msg\migrate\File\<YYYY-MM>\<原名>` |
| 视频 | `FileStorage\Video\<名>` | `msg\migrate\Video\<YYYY-MM>\<名>`（**也有月份层**） |
| 表情 | `FileStorage\CustomEmotion\<XX>\<内容md5 大写>` | `business\emoticon\{Persist,PersistStore,Thumb,ThumbStore}\…` |
| 语音 | **不在文件系统里**，在 `MediaMSG0.db` 的 `Media` 表 | 迁移后进 4.x 自己的库 |

要点：

* 4.x 的图片文件名是 **`<内容md5>_W.dat`** —— **带内容哈希**；
  3.9 侧是**数字名**。所以**不能按文件名比对两侧**，只能用内容或 inode。
* **`<会话md5>` 两侧是同一个值** —— 都是 `md5(StrTalker)`。这是最有用的锚点。
* 迁移**基本不搬表情**：3.9 的 `FileStorage\CustomEmotion` 文件，在 4.x 的
  `business\emoticon` 下**按名字和按内容都找不到**（抽样 10/10 未命中）。
  ⚠️ **但旧版本文档由此推出的"表情渲染走 `emoticon.db` 登记、光有文件不够"是错的** ——
  4.1 的表情渲染走的是 `cache\<YYYY-MM>\Emoticon\`，是**文件层**（见 §5.5）。
* 迁移**不会**把大二进制复制过去 —— 它建**硬链接**（§2.3），
  所以"目录没变大"是**正常现象**，不是漏迁。

链接卡片、图片、语音都**不**转圈。

完整机制见 §5.5。

### 5.5 表情缓存与「懒加载取回」机制（**实测确认**，M1 修订）

> ⚠️ **本节在 M1 晚被重写。** 旧版本的两条结论都被推翻了：
> 「4.x 不会去取、缺的拿不回来」和「必须逐条转发触发一次」。
> 按本仓库的纪律，旧结论连同「错在哪」保留在 §5.5.5。

4.1 渲染 `Type=47` 时查的是**缓存**，不是表情库：

```
<账号根>\cache\<YYYY-MM>\Emoticon\<前2位>\<小写32hex>
```

#### 5.5.1 转圈是 4.x 的原生行为（**实测确认**）

* 用户对照观察：**一批较新的表情**（与本次迁移**毫无关系**，不是搬过来的那批）同样**先转圈、不到 1 秒就加载出来**。
* ⇒ **转圈 ≠ 迁移坏账**：它只表示「气泡已渲染、内容还没到手」。
  差异只在**延迟**：新表情 <1 秒；十年前的表情要几秒到一分钟，但**实测确认会出来**，只是慢。
* ⇒ 判据因此从「转不转圈」改成「**不转发、只等一会儿会不会好**」——答案是**会**（§5.5.2）。

#### 5.5.2 客户端会联网按指纹取回（**实测确认**）

证据：

1. **缓存持续活跃。** 用户翻过会话之后，缓存 `cache\<YYYY-MM>\Emoticon\<前2位>\<小写32hex>`
   不断新增 / 改写 —— 例如 **M1** 一个 **40 分钟**窗口里就有 **572** 个文件变动。
   更早那个快照（M1 上午的一个 9 分钟窗口）单窗口新增 **421** 个文件，其中 **10 个**
   正属于原先判「本地无源」的那批。
2. **时间。** 那 10 个文件是在**迁移后 8 分钟里**才出现的。
3. **穷尽否定搜索。** 这 10 个名字在 ① 3.9 的 `FileStorage\CustomEmotion\`、② 2.x 的原始归档卷、
   ③ 4.x 除 `cache\` 外的整棵树、④ 其它实验目录 —— **一处都没有**（`find` 全空）
   ⇒ 本地**不可能凭空产生，只能来自网络**。
   * 注脚（**一个假阳性**）：把搜索范围再扩到 `AppData\Roaming` / `AppData\Local` / `ProgramData` /
     程序安装目录后，确实在**一个第三方同步工具**的目录下搜到一个同名文件 —— 它属于**另一个微信号**，
     路径里还带着别人机器上的中文目录名；但它只有 **46 字节**、开头是 ASCII `FileSize`，
     那是**同步工具的占位桩文件**，不是真图。
     ⇒ 「本机不存在可本地派生的原件」这个结论**仍然成立，而且更硬**。
   * 可复用的一条：**按文件名搜到的路径，必须验证大小 / 内容，不能只看文件名**（另见 `../appendix/pitfalls.md` §6）。
4. **按会话回流率**（只**打开会话、翻过去、等一会儿**，**没有**做任何转发）。
   279 个「本地无源」的表情里，**已回流 153 个（55%）**，
   其余的 **126 个全部落在用户还没重新打开过的会话里**：

   | 会话（已匿名） | 该会话的「本地无源」数 | 已回流 | 比例 |
   |---|---:|---:|---:|
   | 一个十年前那批里的表情群 | 144 | **144** | **100%** |
   | 一个小群 | 4 | **4** | **100%** |
   | 一个校友群 | 2 | **2** | **100%** |
   | 另两个会话 | 各 1 | 各 1 | **100%** |
   | **279 个合计** | **279** | **153** | **55%** |

   用户实测：翻的时候**不少还在转圈，但基本上 10 秒内就直接加载显示**。

⇒ **凡是用户真正翻过的会话，回流率都是 100%。** 「无解」的真实含义只是**「我还没打开它」**。

**一个教训：别把「快照」当「能力上限」（实测确认）。**
这一轮一开始，我们按**某一时刻的缓存快照**统计，得到「一个十年前那批里的表情群只回流 1.4%」，
差点又把它写成「这个会话基本取不回来」。实际只是**用户当时没翻到那一段**
（那批名字集中在更早的一段，而用户只翻了较晚的一半）。
等用户从头刷一遍，**144/144 全部回流**，且基本 **10 秒内**就出来。
这与 §5.5.5 的「4.x 不会去取」是**同一个毛病的两次发作**：把「某一时刻没看到」当成了
「能力上限」。⇒ 判据要落到「**翻过、等过之后会不会好**」，而不是「现在磁盘上有没有」。

**一句话**：4.x 手里只要有**指纹**（消息里的 32 位 hex 名字），内容就**随时可以联网取回**；
「本地没有原件」**不等于**「拿不回来」，**更不等于**「打开会话也拿不回来」。

#### 5.5.3 协议层：消息里同时记着「哪个包 + 哪张图」（**实测确认**）

对我们已有的**只读库副本**做字段统计（只读查询，不做任何解密）：

| 项 | 数 |
|---|---:|
| `message_0.db` 里 `Type=47` 行 | 995 |
| 其中带 `md5="…"` 属性 | **948** |
| 不同表情名 | **683** |
| 另外带 `productid="…"`（**表情包 id**） | **438** |

原文形如（属性值已截断）：

```
<msg><emoji fromusername="…" tousername="…" type="2" idbuffer="media:0_0"
  md5="a6d956ad3f2270167f2abc6551c328fb" len="31019"
  productid="com.tencent.xin.emoticon.worldcup" androidmd5="…" …></emoji></msg>
```

`productid` 例：`com.tencent.xin.emoticon.worldcup`、`.baozouen`、`.luoxiaohei`、`.midautumn`、
`.bubblepup2`、`.bidiu`，以及 `…emoticon.person.stiker_<时间戳><hex>`（个人表情包）。
⇒ 消息里**同时记着「哪个包 + 哪张图」**，这和「按指纹联网取回」是自洽的。

#### 5.5.4 迁移夜的缓存写入（**推断**）

**M0（迁移当晚）**的**深夜 9 分钟窗口**里，有 **292** 个文件被写入缓存：
其中 **202** 个属于「迁移后本来就正常」的那 213 个名字、**90** 个未被任何消息引用。

⇒ **推断**（措辞有意弱）：迁移 / 首次加载时，客户端**已经**把一部分（**较新的那部分**）表情取回本地了。
为什么恰好是较新的那部分，**未验证**。

#### 5.5.5 被推翻的旧结论（**保留**）

| 旧结论 | 实际 | 错在哪 |
|---|---|---|
| **「4.x 不会去取」**：缺的表情本地找不到、4.x 也不去取，于是**无解** | 客户端**会联网按指纹取回**（§5.5.2 四条独立证据） | 只统计了**本地磁盘**，没把「等待期间的网络回填」纳入观察窗口；两次统计之间也没有对齐「这些会话是否被打开过」 |
| **「必须逐条转发触发一次」** | **打开会话 + 等待**同样会加载；转发只是**逼客户端立刻渲染这一条**，作用是**加速** | 把「转发时的成功」当成了**因果**。当时 4 个样本 **100%** 成功，但那只是**相关**；正确判据是「不转发、只等待会不会好」，答案是**会** |

「**合并转发无效**」**仍然成立**，但解释要改：合并转发只把多条打成一张**聊天记录卡片**、
**不逐个渲染**表情，所以不会触发逐条加载 —— 这反倒说明加载的触发点是**逐条渲染**，不是某种批量动作。

> **同一个毛病还有一次发作**：把**某一时刻的缓存快照**当成「能力上限」——
> 见 §5.5.2 末尾的「一个教训：别把『快照』当『能力上限』」。

#### 5.5.6 缓存与校验行为（沿用，**实测确认**）

| # | 实测结论 |
|---|---|
| 1 | **迁移基本不搬表情**：迁移前 683 个被消息引用的名字里，这个缓存只命中 **204** 个、`business\emoticon\**` 只命中 **2** 个 |
| 2 | **客户端会校验「内容 ↔ 文件名」**：内容与文件名不符的图会被**删掉**；`V1MMWX` 容器（内层 md5 = 文件名）会被**接受** |
| 3 | 把 3.9 那 246 个有源文件拷进 `cache\<当月>\Emoticon\` 后，命中数 **204 → 403** |
| 4 | 取回后客户端会**本地解码**该文件、**用它自己的容器重写**缓存文件（`3964140A…` 24,011 B → 24,016 B；`CE76D3DE…` 44,073 B → 29,568 B），此后气泡与转发预览都正常 |

#### 5.5.7 边界与未验证

边界（都实测过）：

* **不需要访问 4.x 数据库、不需要动任何 `.db`**。
* **需要网络**（**已基本确定**，不再是「推断」）：那 10 个文件在**本地四处穷尽搜索后无处可寻**，
  只能来自网络。**但走的是 CDN 还是 API，属于未验证**（需要抓包）。
* ⚠️ **`business\emoticon\Persist` 那条路是关着的**：往里放的野文件会被客户端**删掉**
  （它是索引驱动的）。**渲染走 `cache\`，不是它。**

## 7. 一句话

**迁移已经通了（§2，有逐项实测），而且是官方原生路径。**
