# 微信 3.x 的媒体布局：按消息类型逐条对照

### Media layout in WeChat 3.x, message type by message type

> 实测环境：WeChat **3.9.12.56**（x86）/ 源数据 WeChat **2.0.0.37**（十年前编译，x86）
> 一句话：**媒体不存字段、存文件；客户端按「记录下来的路径」找媒体，不按内容哈希。**
> 所以「路径由你写、文件由你放」，两边一致就能显示 —— 不需要反推哈希，也不需要复刻客户端的命名规则。

### 0.1 内容来源的二分：决定"要不要盘点它"（**结论**）

上表里的类型，按**内容是怎么到 4.x 的**可以分成两类 —— 这决定了"本地有没有"这种盘点**对谁有意义**：

| 来源 | 哪些类型 | 迁移时怎么办 |
|---|---|---|
| **① 本地放置型** | 图片、语音、视频、文件，以及自定义表情的**原件** | 必须**在旧树里真的存在**，并由旧版本客户端 / 迁移功能 / 我们的工具放到位。**本地缺了就是缺了** |
| **② 按指纹取回型** | 自定义表情（`Type=47`）的**内容** | 本地只需要那个 **32 位 hex 指纹**；内容由客户端**联网按「表情包 id + md5」懒加载取回**（§6.1，**实测确认**） |

⇒ 只有**第 ① 类**才需要"本地有没有 / 缺多少"的盘点；
第 ② 类里"本地没有"**不等于**取不回来 —— 我们一度把这两件事混为一谈，见 `../appendix/pitfalls.md` §17。

## 1. 路径的基准点：`WeChat Files` 根 + 账号目录

`BytesExtra` 里记的路径是**相对数据根**的，**第一段就是账号目录**，没有盘符、没有前导分隔符：

```
<ACCOUNT>\FileStorage\File\<YYYY-MM>\<原始文件名>              ← 客户端自己写下的样例
<ACCOUNT>\FileStorage\MsgAttach\<md5(StrTalker)>\Image\<YYYY-MM>\<name>.dat
```

* **实测确认**：上面第一条是客户端自己发出一个文件时，写进 `BytesExtra` 子类型 4 的原文。
* 解析时按 `os.path.join(<DATA_ROOT>, <记录的路径>)` 拼；`<DATA_ROOT>` 就是 `WeChat Files` 本身
  （Windows 上通常是 `C:\Users\<user>\Documents\WeChat Files`，或注册表 `FileSavePath` 指向的位置）。
* **2.x 记的是当年那台机器的绝对路径**（含盘符与用户目录），在本机解析不到 ⇒
  气泡显示「已被清理」/「文件已过期」。导入十年前的媒体时要修的其实只有这一件事：
  **把路径改写成本机成立的值**。
* `<YYYY-MM>` 取 `MSG.CreateTime`（本地时区），形如 `<YYYY>-08`。
* `<md5(StrTalker)>` 是**会话用户名**（`MSG.StrTalker`）的 MD5 小写 hex —— 不是消息内容的哈希。

## 2. `BytesExtra` 是两层 protobuf

`MSG.BytesExtra` 不是自定义结构，就是一层 protobuf，但**按值的类型分装在两个外层字段里**（实测确认）：

```
外层 repeated field 1  =  varint 类： { 1: 子类型, 2: varint 值 }
外层 repeated field 3  =  bytes  类： { 1: 子类型, 2: 字节值 }
```

已知子类型：

| 子类型 | 类型 | 含义 |
|---|---|---|
| 1 | bytes | `fromusername`（发送者用户名） |
| 2 | bytes | `clientmsgid`。**对图片/文件不是内容 MD5**（见下） |
| 3 | bytes | 语音 = `voicelength`（毫秒）；图片 / 视频 = 缩略图路径 |
| 4 | bytes | 原文件路径（图片 / 文件 / 视频）；**表情 = 裸名字**（不是路径）—— 但 995 条 `Type=47` 里**有 28 条是路径**，指向 `Image\<会话>_<时间戳>_<n>.gif`，全部存在（见 §3.5） |
| 5 | varint | 「播放过」标记 —— 客户端成功播放一条语音后才补上 |
| 6 | varint | 未定位，出现在部分图片行 |
| 7 | bytes | `<msgsource>` XML |
| 16 | varint | 未定位，客户端自己写的行里出现过 |
| 32 | varint | 未定位，出现在文件行 |

两条容易踩的：

* **顺序不影响播放**（实测确认）：客户端的序列化把 `field 1` 全部排在 `field 3` 之前；
  我们手工构造时曾把 `field 3` 排在前面（子类型序列 `[7,5,2,3,1]`），照样能播。
  所以不必模仿客户端的字段顺序。
* **子类型 2 不是内容哈希**（实测确认）：四个内容完全相同的附件，在库里带着四个**不同**的
  子类型 2 值。不要用它匹配文件 —— 客户端也不会。

## 3. 逐类型

### 3.1 Type=1 文字

无媒体。十年前那批历史共 **约 3.2 万** 条（实测确认），正文全部在 `MSG.StrContent` 里。

### 3.2 Type=3 图片

| | |
|---|---|
| 路径记录 | 子类型 4 = 原图，子类型 3 = 缩略图 |
| 目标目录 | `<ACCOUNT>\FileStorage\MsgAttach\<md5(StrTalker)>\Image\<YYYY-MM>\<name>`<br>缩略图同层换成 `Thumb\` |
| 编码 | **单字节 XOR 0xA0**（实测确认） |
| 源 | 十年前那份归档的 `Data\` 与 `Data\Tiny\` **本来就是 XOR 0xA0**，原样复制即可 |

XOR 的依据（实测确认）：`5F 78 5F 40` ^ `A0` = `FF D8 FF E0`（JPEG 头）。

* 文件名沿用 2.x 记录的 basename（`<...>.dat`），不改名、不重算哈希。
* 结果：**1,383** 张原图 + **1,385** 张缩略图全部正常显示。
* ⚠️ **别用写死的 `localId` 上界**：我们第一版写了当时误以为的最大值，尾巴 44 行图片整体被漏掉，
  症状是客户端日期视图卡死。见 `../appendix/pitfalls.md` 第 1 条。

### 3.3 Type=34 语音

**语音不在文件系统里。** 音频以 BLOB 存在数据库里（实测确认）：

```
库   : <ACCOUNT>\Msg\Multi\MediaMSG0.db
表   : Media(Key TEXT PRIMARY KEY, Reserved0 INT, Buf BLOB, Reserved1 INT, Reserved2 TEXT)
Key       = 2^40 + MSG.localId          （前缀常量，不是时间、不是会话）
Reserved0 = MSG.MsgSvrID
Buf       = 裸音频字节，\x02#!SILK_V3（SILK）或 #!AMR（AMR）
```

* 这个形状的权威来源是**客户端自己写下的那一行** —— 它给自己发出/收到的语音写的就是这样。
* ⚠️ **光把 `Media` 行写对还不够**：客户端还要先认可这条消息属于「本库纪元」，才会去查本地媒体。
  缺这一步的表现是「气泡有时长、点下去变红感叹号或无限转圈」。
  机制与修复见 `voice-start-time.md`（`DBInfo` 的 `Start Time`）。
* 不要碰 `Msg\Media.db` 的 `MediaInfo` 表：它属于「聊天记录 / 收藏」子系统，3.9 **建表但从不写**
  （实测确认），往里面搬数据没有任何效果。

### 3.4 Type=43 / 62 视频

| | |
|---|---|
| 2.x 记录 | 子类型 3 = 缩略图 `.jpg` 路径，子类型 4 = 视频 `.mp4` 路径 |
| 2.x 文件 | `<账号目录>\Video\<md5>.mp4` / `<md5>.jpg`，**明文**（实测确认：mp4 头里有 `ftypmp42`） |
| 3.x 目标 | `<ACCOUNT>\FileStorage\Video\<name>` |

**扁平还是按月？** 3.9 自己建了 `FileStorage\Video\`，但**是空的、没有任何子目录**；而
`FileStorage\File\` 有 `<YYYY-MM>` 子目录（那是客户端自己写文件时选的）。所以最初的选择是
**推断**：沿用 2.x 的扁平排布（mp4 与 jpg 同目录），只把根前缀换成 `FileStorage\Video\`。

**实测确认：91/91 全部可播。** 如果哪天这个假设不成立，下一个候选是加 `<YYYY-MM>` 子目录。

这一步除了改 `BytesExtra` 的子类型 3/4，不改数据库里别的任何东西。

### 3.5 Type=47 自定义表情

* 2.x 的子类型 4 **绝大多数是**一个裸的 32 位大写 hex 名字，不是路径 —— 没有机器相关成分，
  所以**不需要改写**，只要把文件放到客户端会去找的地方（实测确认）。
  （例外：995 条里有 **28 条**是路径，指向 `Image\<会话>_<时间戳>_<n>.gif`，全部存在。）

  ```
  <ACCOUNT>\FileStorage\CustomEmotion\<名字前两位>\<名字>
  ```

* **文件名是客户端要去查的"键"，但键的算法取决于这个文件是什么**（实测确认）：
  * **普通图片（GIF / PNG / JPEG）**：`<名字>` == **文件内容 md5**。
    旧版本文档在 2.x 归档 `CustomEmotions/` 上校验过（记为 12/12）；本轮复核一个普通 GIF 样本，1/1 一致。
  * **`V1MMWX` 容器**：`<名字>` == **里面那层原图**的 md5，**不是容器文件本身的 md5**。
    本轮抽 5 个样本：普通 GIF 1/1 一致、`V1MMWX` **4/4 不一致**。
  ⇒ 旧版本文档把第一条当成了通用规则 —— **这一点是错的**。
* 客户端自己存的表情文件**不是明文 GIF**，而是 `V1MMWX` 开头的加密封装
  （`56 31 4d 4d 57 58` 之后是高熵数据）。单字节 XOR 试遍 256 种都不出 `GIF8` / `PNG` / `JPEG`；
  用文件名当 AES 密钥配几种 IV/偏移组合也不成立 ⇒ **封装格式仍未解开**。
* 做法：**放明文 GIF** —— **实测确认可行**，动画表情显示正常。
  但旧版本文档由此推断"客户端会**嗅探**格式"，这个**归因也偏了**：4.x 侧实测显示客户端是在
  **校验「内容 ↔ 文件名」**（内容不符的文件被删掉、`V1MMWX` 被接受并重写成它自己的容器 ——
  见 `4x-migration.md` §5.5），不是无条件嗅探。
  万一某个版本只认 `V1MMWX`，这些文件会被直接忽略，**没有任何破坏性**；
  而且这一步**不改数据库**，是纯文件放置，随时可回退。
* ⚠️ **同一个目录里其实混着两种"出身"**（实测确认，见 §5）：普通图片那 232 个是**十年前的原始文件**，
  `V1MMWX` 那 229 个是 **3.9 客户端在迁移当日自己批量写出来的**（mtime 集中在同一个 38 秒窗口）。
  这两个数字决定了后面哪些能救、哪些不能。

### 3.6 Type=49 文件 vs 链接卡片（一定要分清）

Type=49 是「appmsg」容器，里面到底是文件、链接还是表情，取决于 `StrContent` 里的内层 XML：

| 内层 | 含义 | `BytesExtra` 里是什么 | 处理 |
|---|---|---|---|
| `<type>6</type>` | 文件 | 子类型 4 = **真文件路径** | 本文档处理（186 行） |
| `<type>5</type>` | 图文 / 链接卡片 | `.f3.s3` = 封面**缩略图**路径 `Attachment\<md5>_t.jpg`；`.f3.s4` = 封面**原图**路径 `Attachment\<md5>`（无扩展名）。旧版本文档这里写的是"**封面图的 md5**"—— **错**，字段级重扫（`4x-migration.md` §5.3）确认两个都是路径 | **不必动**：4.1 渲染卡片时**根本不加载封面**（见 §6） |
| `<type>8</type>` | GIF 表情 | 见 §3.5 | 不是文件 |

> 计数口径：内层 `<type>5</type>` 共 **1,687** 条、`<type>6</type>` **186** 条、`<type>8</type>` 5 条。
> 旧版本文档记的是 `<type>5</type>` **1,724** 条 —— 这个差**不是数据变了，是口径变了**（已查清）：
> 旧的 1,724 用的是"`Type=49` 且内层不是文件"这种粗分法，把 **37 条内层根本没有 `<type>` 的行**
> 也算了进去。**以新口径为准。**
> （`Type=49` 全量 1,923 条的分布：`<type>5` 1,687、`<type>6` 186、无 `<type>` 38、
> `<type>8` 5、`<type>2` 2、`<type>7` 2、`<type>17` 1、`<type>1` 1、`<type>2000` 1。）

* 目标：`<ACCOUNT>\FileStorage\File\<YYYY-MM>\<name>`，
  **明文存放、不异或**（实测确认：归档里的 `.doc` 以 `d0cf11e0a1b11ae1` OLE2 头开始）。
* 只处理「basename 在归档里确实存在」的行。否则你会把路径写成一个不存在的文件，
  气泡从「已被清理」变成「打不开」—— 比原来更糟。
* `<totallen>` 是消息里声明的字节数，可用来核对（实测确认：与归档文件大小一致）。
* 结果：186 条引用里 **132 条恢复**（78.7 MB）。

## 5. 做不到的部分（动手前先读这一节）

* **54 个文件附件在任何副本里都不存在**（实测确认）。原因不是我们没找，而是 2.x 只在用户当年
  **点开/下载过** 时才把文件落盘。我们扫了 **9 个根、239,119 个文件**，只命中 **1 个同名而内容不同**
  的文件：库里记 31,381 B 的那个 `Desktop.zip`，实际找到的是 4.1 MB / 77 KB / 14 MB 的现代文件。
  ⇒ 用「同名匹配」跨目录找文件会误配；匹配到的文件请先比大小，不要直接当成原件。
* **表情缺口靠归档补不齐**（实测确认，口径如下，请按同一口径复核）：
  * `Type=47` 消息 **995** 条；`BytesExtra` 子类型4 去重后共 714 个取值，其中符合
    「32 位大写 hex」这个名字口径的 **683** 个 —— 这就是客户端真正需要的名字集合。
  * 现在 `CustomEmotion\` 下共 **461** 个文件，其中命中需求的 **246** 个 ⇒ **仍缺 437 个**。
  * ⚠️ **「437」与「279」是两个不同的集合**（M1 晚口径，**实测确认**）：

    ```
    683 个被消息引用的表情名
     ├─ 246 个在 3.9 里有源文件              （manifest：placed 199 + skipped 47）
     └─ 437 个在 3.9 里没有源文件
          ├─ 158 个 4.x 早就自己存进了缓存   （所以一直正常）
          └─ 279 个 既转圈、又无本地源       ← 原先判「无解」的那批
    ```

    校验：`199 + 47 = 246`；`246 + 437 = 683`；`158 + 279 = 437`。
    这 279 个**已回流 153 个（55%）**，且**凡用户重新翻过的会话都是 100%**（见 §6.1）。
  * 而十年前那份归档里**总共只有 238 个表情文件**，能补进需求的是 **232** 个（其余 6 个不是库里需要的名字）。
    归档里**确实没有**剩下那 437 个。
  * ⚠️ **修正一处旧结论。** 旧版本文档由上面这条推出「**剩下 437 个在上游就不存在**」——
    **这句站不住**。我们把 3.9 目录里那 229 个 `V1MMWX` 的内容 md5 拿去扫归档 **5,670 个文件**
    （`Data/` 还额外做了 XOR 0xA0 解码），**只命中 7 个**，其中 3 个还是 `Image/` 里的聊天 GIF
    ⇒ 那 229 个**不是从归档来的**，最可能是 3.9 在迁移当日**从网络取的**。
    ⇒ 能站住的说法只有：**归档里没有**；至于上游还有没有，当时属于**未验证**。
    （后来 4.x 侧已实测能**联网按指纹取回**缺的表情 —— 见 §6.1 与 `4x-migration.md` §5.5.2。）
    （我们**没有**抓到直接的下载证据 —— 3.9 当天的日志 `.xlog` 是私有帧格式，本机解不开。）
  * 计数口径提醒：上面几个数字分别按「消息条数 / 子类型4 去重取值 / hex 名字 / 目录文件数 /
    命中需求的文件数」统计，**不能直接相加**；先说清定义再比数字。
* 与媒体无关的另一个缺口：跨度末尾之后的**文字正文**随旧磁盘分区消失，无法恢复。

## 6. 4.x 侧的对应布局（**实测确认**，M1）

> 本节是 `4x-migration.md` §4 的摘要；迁移流程与验收见 `4x-migration.md` §2，
> 表情的缓存与「懒加载取回」机制见 `4x-migration.md` §5.5。

| 消息类型 | 3.9 路径 | 4.x 路径 |
|---|---|---|
| 图片（原图/缩略图） | `FileStorage\MsgAttach\<会话md5>\Image\<YYYY-MM>\<数字名>.dat` | `msg\attach\<会话md5>\<YYYY-MM>\Img\<内容md5>_W.dat` |
| 文件附件 | `FileStorage\File\<YYYY-MM>\<原名>` | `msg\migrate\File\<YYYY-MM>\<原名>` |
| 视频 | `FileStorage\Video\<名>` | `msg\migrate\Video\<YYYY-MM>\<名>`（**也有月份层**） |
| 表情 | `FileStorage\CustomEmotion\<XX>\<名字>` | **`cache\<YYYY-MM>\Emoticon\<前2位>\<小写名字>`** ← 渲染走这里；`business\emoticon\{Persist,PersistStore,Thumb,ThumbStore}\…` 是**索引驱动**的，不是渲染路径 |
| 语音 | **不在文件系统里**，在 `MediaMSG0.db` 的 `Media` 表 | 迁移后进 4.x 自己的库 |

三条要点：

1. **两侧的嵌套顺序正好相反**（3.9 是 `<会话>\Image\<月>`，4.x 是 `<会话>\<月>\Img`），
   按 3.9 的结构去 4.x 里找会**一个都找不到**。
2. **`<会话md5>` 两侧是同一个值**（都是 `md5(StrTalker)`）—— 这是最可靠的锚点。
3. **4.x 侧的图片名带内容 md5，3.9 侧是数字名** ⇒ **不能按文件名比对两侧**，
   只能按内容或 inode 比。

⚠️ **`BytesExtra` 子类型 4 的含义随消息类型变化**（字段级明细见 `4x-migration.md` §5.3）。

⚠️ **旧版本文档在这里写过"`Type=49` 存的是旧机器的绝对路径，会导致无限转圈" —— 已被证伪。**
4 张真实链接卡片在 4.1 上全部正常渲染；**4.1 根本不加载卡片封面**。详见 `../appendix/pitfalls.md` §16。

### 6.1 表情：4.x 的渲染缓存与「懒加载取回」机制（**实测确认**，M1）

4.1 渲染一条 `Type=47` 表情时查的是**缓存**，不是表情库：

```
<账号根>\cache\<YYYY-MM>\Emoticon\<前2位>\<小写32hex>
```

四条实测：

1. **迁移基本不搬表情**：迁移前 683 个被消息引用的名字里，这个缓存只命中 **204** 个、
   `business\emoticon\**` 只命中 **2** 个。缺的几乎全是 3.9 侧那种 `V1MMWX` 容器（见 §3.5）。
2. **客户端会校验「内容 ↔ 文件名」**：把内容与文件名不符的图放进这个缓存，**会被删掉**；
   放 `V1MMWX` 容器（内层 md5 = 文件名）则被**接受**。把 3.9 那 246 个有源文件拷进去之后，
   命中数从 **204 升到 403**。
3. **光有文件、气泡先转圈是正常的** —— 它只是「内容还没到手」，**不是永远不出来**。
   正确做法是**打开会话、翻过去、等一会儿**：客户端会**联网按指纹取回**。
   实测（M1）：279 个「既转圈、又无本地源」的表情里**已回流 153 个（55%）**；
   **凡用户真正翻过的会话都是 100%**（一个十年前那批里的表情群 144/144、一个小群 4/4、
   一个校友群 2/2、另两个各 1/1），用户实测**基本 10 秒内**就加载出来；
   剩下的 126 个**全部落在用户还没重新打开过的会话里**。
   * ⚠️ **别把「快照」当「能力上限」**：一度按某一时刻的缓存快照算，得到「一个十年前那批里的表情群
     只回流 1.4%」，其实只是**用户当时没翻到那一段**；从头刷一遍就是 **144/144**。
   * **转发**的作用只是**逼客户端立刻渲染这一条**，属于**加速**，**不是必要条件**
     （旧「必须逐条转发」已证伪）。「**合并转发**」无效 —— 它只打成一张聊天记录卡片，
     **不逐个渲染**表情，所以不会触发逐条加载。
   * **需要网络**：那批「既转圈又无本地源」的名字在 3.9 的 `FileStorage\CustomEmotion\`、2.x 原始归档卷、
     4.x 除 `cache\` 外的整棵树、其它实验目录里**一处都没有**（`find` 全空）
     ⇒ 只能来自网络。**但走 CDN 还是 API，属于未验证**（需要抓包）。
     （一个**假阳性**：搜索扩到 `AppData` 与程序安装目录后，在**一个第三方同步工具**的目录下
     搜到过同名文件 —— 它是 **46 字节**、开头 ASCII `FileSize` 的**占位桩**，不是真图，
     而且属于另一个微信号。⇒ 「本地不存在可派生原件」的结论**更硬**。）
   * **不需要 4.x 的密钥、不需要动任何 `.db`**（实测确认）。
   * **长期成功率未验证**：腾讯侧可能下架 / 清理老表情包；转发时出现的**版权保护**失败提示
     是个值得警惕的信号。要测就给一个会话**翻到底、等够时间**再统计。
4. ⚠️ **`business\emoticon\Persist` 那条路是关着的**：往里放野文件会被客户端删掉
   （它是索引驱动的）。渲染走的是 `cache\`，不是它。
   （旧版本文档写过"表情走 4.x 的 `emoticon.db` 登记，光有文件不够" —— 这个**归因是错的**。）

* 规模与待办清单：`private/reports/sticker-todo.csv`。
