# 微信 3.9 的 SQLCipher 参数（和 2.x 一模一样，但有两个会白跑一整轮的坑）

### SQLCipher parameters for WeChat 3.9.x — identical to 2.x, with two traps

> 实测环境：WeChat **3.9.12.56**（x86）/ Windows 11 x64
> 验证方式：**逐页 HMAC-SHA1 校验整库**（每一页都算，不是抽样），外加往返自检与 `integrity_check`
> 结论：加解密参数与 2.0.0.37 **完全相同**；差别只在页头那两个字节

---

## 0. TL;DR

按重要性排三层：

1. **最大的坑**：3.x 的 page-1 明文头是 `10 00 02 02`（**WAL 模式**），2.x 是 `10 00 01 01`。
   如果自检工具拿 `01 01` 当「这是一个 SQLCipher 库」的判据，**整代 3.x 库会被全部漏掉**。
   我们为此白跑过一整轮扫描。（**实测确认**）
2. 参数与 2.x 一字不差：page 4096 / 每页保留 48 / PBKDF2-HMAC-SHA1 64000 / 每页 AES-256-CBC +
   HMAC-SHA1。（**实测确认**）
3. **一个库一把密钥** —— 由每个文件自己的 salt 决定。（**实测确认**）

---

## 1. 参数总表

| 项 | 值 | 说明 |
|---|---|---|
| `page_size` | **4096**（`0x1000`） | 与 2.x 相同 |
| 每页保留段 | **48** 字节（`0x30`） | = IV 16 + HMAC-SHA1 20 + padding 12 |
| KDF | **PBKDF2-HMAC-SHA1** | 用来从账号密钥派生 AES 密钥 |
| 迭代次数 | **64000**（`0xFA00`） | 与 2.x 相同 |
| 页加密 | **AES-256-CBC，每页独立 IV** | IV 不派生、直接随机存页尾 |
| 页完整性 | **HMAC-SHA1**，每页一枚 | 覆盖 `ciphertext ‖ IV ‖ le32(页序号+1)` |
| HMAC 位置 | `[PAGE-32 : PAGE-12]`（= `[4064:4084]`） | 20 字节 |
| IV 位置 | `[PAGE-48 : PAGE-32]`（= `[4048:4064]`） | 16 字节 |
| 尾部 padding | `[PAGE-12 : PAGE]` | **不在 HMAC 覆盖范围内** |

> 我们在 MSG0.db 上逐页验证通过后才把它当作事实 —— 这份参数不是抄来的假设，
> 而是全库每页都算过 HMAC 的结果。（**实测确认**）

---

## 2. 每页的字节布局

```
page 0    : [ salt 16 ][ ciphertext 4032 ][ IV 16 ][ HMAC-SHA1 20 ][ pad 12 ]
page i>0  : [ ciphertext 4048 ]           [ IV 16 ][ HMAC-SHA1 20 ][ pad 12 ]
```

两个容易看漏的点：

* **page 0 的 `SQLite format 3\0` 不落盘**。文件开头那 16 字节是 **salt**，明文页头的前 16 字节
  （也就是那句 magic）在加密时被 salt 占位替换掉了。所以「解密出来的 page 0」需要把开头补回 magic
  才能交给 SQLite 读。
* **`pad 12` 不被 HMAC 覆盖**，可以随便写（我们回写时固定填零，与客户端一致）。

---

## 3. 密钥派生与 HMAC

```
aes_key  = PBKDF2-HMAC-SHA1( <MASTER_KEY>, salt, 64000, 32 )     # 32 字节，直接当 AES-256 密钥
mac_salt = salt XOR 0x3A                                          # 16 字节
mac_key  = PBKDF2-HMAC-SHA1( aes_key, mac_salt, 2, 32 )           # 注意只有 2 轮
HMAC     = HMAC-SHA1( mac_key, ciphertext ‖ IV ‖ le32(page_index + 1) )
```

* `salt` 就是文件开头的 16 字节。**每个库文件不同**，所以每个库的密钥也不同。
* `<MASTER_KEY>` 是账号级的中间量；上面的式子说明的是**各值之间的关系**，不是操作步骤。
* HMAC 里那个 `page_index + 1` 是 **1 起算**的页序号，小端 4 字节。**这是最容易写错的一处**：
  写成 0 起算会导致除第 0 页外全部不匹配。

**一次 AES 块解密就能判定一个候选密钥**（这也是扫描器快 16000 倍的原因）：
解密 page 0 的密文（文件偏移 16 起）的第一个 AES 块，明文应当以

```
10 00  <w> <r>  30 40 20 20
```

开头 —— `0x1000` 是页大小，`0x30` 是保留段 48，`40 20 20` 是 payload fractions 64/32/32，
而 `<w> <r>` 就是下一节的代际标志。（**实测确认**）

---

## 4. 坑一：`10 00 02 02` —— 3.x 是 WAL 模式

同一份参数下，**两代的页头只差两个字节**：

| 代 | 明文 `[16:24]` | `<w> <r>` | 日志模式 |
|---|---|---|---|
| 2.0.0.37 | `10 00 01 01 30 40 20 20` | `01 01` | rollback journal |
| 3.9.12.56 | `10 00 02 02 30 40 20 20` | `02 02` | **WAL**（运行时会生成 `-wal` / `-shm`） |

`<w>` 和 `<r>` 是 SQLite 页头里的 **file format write/read version**：`1` = legacy，
`2` = WAL。3.9 用 WAL，所以运行时你能在旁边看到 `MSG0.db-wal`、`MSG0.db-shm`。

**这个坑的代价**：如果扫描/自检的判据写成「解密出来是 `10 00 01 01` 才算命中」，
那么所有 3.x 库都会被判为"不是 SQLCipher 库"而跳过 —— 扫描器会**正常结束、报告 0 命中**，
不会报错。我们就是这样白跑了一整轮。（**实测确认**）

**正确写法**：判据只看 `10 00` + `0x30` 保留段（必要时再看 payload fractions），
把 `<w> <r>` 当作**输出信息**（告诉你是哪一代），而不是**准入条件**。

> 顺带一个同族的坑：有人写「完全不依赖 reserve 的扫描」（用 `P2 = D(C2) XOR C1` 之类的性质）。
> 这个思路在 4.1 上给过一次**假阳性** —— 唯一命中经复核是同一个常量同时出现在两个进程里，
> 不是密钥。任何扫描器都必须带**注入式自检**：把一段已知密钥写进临时文件，扫它，
> 能精确命中才允许相信实扫结果。（**实测确认**）

---

## 5. 一个库一把密钥

* `salt` 取自每个文件自己的头 16 字节 ⇒ **每个库一把 `aes_key`**，互不通用。
* 同一账号、同一客户端版本下，密钥**跨时间稳定**：早先取到的密钥，
  能直接解开后来写下的文件。（**实测确认**）
  ⇒ 这条性质是整条迁移路线成立的前提（老库不需要重新登录）。
  （**实测确认**）

## 6. 回写三原则（②③ 才是真正的坑）

### ① 先在明文里把形状设好，再加密；而且**别在解密时顺手改它**

page 0 的页头（页大小、日志模式、保留段）**在密文里面**。加密之后再想去改那几个字节，
只能毁掉这一页的 HMAC。所以顺序永远是：

```
解密 → 在明文里确认/设置 bytes[18:20] 与 bytes[20] → 加密
```

三条实测结论：

* **客户端写出来的 3.x 库是 `10 00 02 02`（WAL）**，保留段 `bytes[20] == 0x30`（=48）。
  `MSG0.db` 与 `MicroMsg.db` 都实测如此。
* ⚠️ **不要在解密函数里"顺手归一化"这两个字节。** 我们的第一版参考实现就是无条件写成
  `01 01`（想着方便用普通 SQLite 工具打开看看），后果有两个：① 往返回写会**静默把客户端的
  WAL 降级成 rollback journal**；② 工具随后打印的"库的页头"其实是**它自己刚改出来的值**，
  于是文档和读者都会以为 3.x 是 `01 01`。**解密就老老实实原样返回**；确实要改，走显式参数，
  并只改**内存里的副本**。（**实测确认**，这是踩过的坑）
* ⚠️ **保留段必须在「空壳」阶段就写对。** 想从 DDL 现造一个 3.x 库时，不能把 DDL 直接灌进一个
  空文件 —— SQLite 核心只会把保留段字节写成 `0`，而**内容建好之后再去改 `bytes[20]`
  会立刻毁库**（每页的单元指针数组整体错位 48 字节）：

  ```
  Tree 3 page 3 cell 0: Offset 4091 out of range 3815..4044
  → database disk image is malformed
  ```

  正解是：**先造一个「1 页、0 表、保留段 48」的合法空壳**，让 SQLite 一开库就从页头读到 48，
  之后建表、插行都会按 `4048 = 4096 - 48` 的可用区布局走。`scripts/wxcom` 里的
  `make_sqlite_shell()` 就是这个空壳的生成器（`wxrows.py` 用它起手）。（**实测确认**）

### ② 按**头部页数**截断后再加密

微信用的 WCDB 会把 `MSG0.db` **预分配**到固定大小：实测见过 `52,428,800` 字节（12,800 页），
把 `Start Time` 前移、客户端滚出新分片之后又见过 `62,914,560` 字节。未用的尾页是**裸零**。

而「无差别加密整个文件」会把那些尾页也变成**合法的 SQLCipher 页** —— 得到一种客户端从不产生的形状。
`pragma page_count` 与头部 bytes 28..32 一致（实测都是 5,135），所以功能上没坏，
但**正确的做法是按头部页数截断**再加密，让客户端自己去重新预分配：

```
npages = int.from_bytes(header[28:32], 'big')      # 大端
truncate(npages * 4096)
```

（**实测确认**）

### ③ 往返比对只能比**可用区**

重新加密必然换新 IV（而且 HMAC 也跟着变），所以"解回来跟原文逐字节相同"这个判据**永远会失败**。
要比的只有 SQLite 真正读取的那段：

```
[0, PAGE - RESERVE) 逐字节相等        # 每页只比前 4048 字节
```

外加"全页 HMAC 0 不符"来证明每页密文都是你自己写的。（**实测确认**）

## 7. 验证配方

一个可以照着抄的验收顺序（四步，缺一步都不算通过）：

| # | 检查 | 通过标准 | 工具 |
|---|---|---|---|
| 1 | 全页 HMAC-SHA1 | **0 页不符**（实测规模：5,135/5,135、5,148/5,148、5,149/5,149 页全通过） | `decrypt_db()` 的 `bad` 计数 |
| 2 | `PRAGMA integrity_check` | `ok` | `sqlite3` |
| 3 | 往返一致 | 解密 → 再加密 → 再解密，**可用区逐页逐字节相等** | 见 §6 ③ |
| 4 | 行级核对 | 行数 / `max(localId)` / 时间跨度 / `TalkerId` 可解析 等（清单见 `row-mapping.md`） | `sqlite3` |

> 只有 1+2+3 全过，才允许把文件拷到客户端目录；`install` 步骤还应当先备份、并在客户端
> **干净退出**（`-wal` 归零）之后才动手 —— 那是另一篇的事，见 `pitfalls.md`。

## 8. 边界：这套参数只对 3.x

本文的参数是在 **3.9.12.56（x86）** 上逐页验证的。**4.x 是另一套布局**
（AES-256-CBC / 页 4096 / 保留段 80 / raw key），见 [`4x-migration.md`](4x-migration.md)。
另外 4.x 是 **64 位**，程序目录里**没有** `libFFmpeg.dll`（与 3.9 的 32 位布局不同）。
