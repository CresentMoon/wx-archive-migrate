# 附件审计：重复与孤立

> 证据标签：**实测确认** / **推断** / **未验证** / **已证伪**。
> 本文只讲**怎么查**和**查出来什么**，不含任何真实文件名、账号名或密钥。
> 复现脚本：`private/tools/wx4_attach_refs.py`（库引用集）、
> `private/tools/wx4_attach_inventory.py`（磁盘清单 + 双哈希）、
> `private/tools/wx4_attach_audit.py`（比对出报告）。
>
> **结论速查**：① 判重**必须按 inode** 算 —— 客户端自己已经硬链接了一部分，
> 按文件数会**高估一倍**；② 只在**字节相同**（`md5_raw` 相等）时才折叠，**不能按文件名**；
> ③ 路径由「目录 + 文件名」共同决定，而目录来自消息时间或接收会话（**都不可改**）
> ⇒ 大部分重复**无法收敛成一个名字**，只能硬链接；
> ④ **已执行**：13,414 个名字 / 6,687 组，路径条目 189,187 条**一个不少**，物理 **−22.897 GB**，可回滚；
> ⑤ 改写库里的路径**主动放弃**（省 0 字节 + 手机合并风险，见 §7.2）。

---

## 1. 为什么要做

迁移完之后，`xwechat_files` 里堆了一批**碎文件**：图片是 `.dat`、文件是原名或 32 位 hex、
还有一堆 `(1) (2)` 后缀。想知道两件事：

1. **哪些文件内容是重复的**（可以合并/硬链接）；
2. **哪些文件是孤立的** —— 客户端自己的库里已经**不再引用**它们了。

「孤立」不等于「没用」，但没有库线索的文件才是**可能**能清的。反过来，**有索引的文件一个都不能动**。

---

## 2. 判定口径

一个磁盘文件算「**有索引**」，只要命中以下任意一条：

| # | 依据 | 覆盖的场景 |
|---|---|---|
| 1 | **文件名**出现在库里的文件名集合 | 文件类附件（appmsg 的 `<title>`、资源表的原始名/本地名、硬链接账本的 `file_name`） |
| 2 | 文件名里的 **32 位 hex**（含去掉 `_<hex>` 后缀后）出现在库里的 id 集合 | 图片/视频（磁盘名就是 **id**，见 §3） |
| 3 | **文件内容 md5**（原始字节，或解开容器后的字节）出现在库里的 id 集合 | 客户端按内容寻址写出来的文件 |

反过来，**三条全不中才算孤立**。这个方向是**故意保守**的：宁可漏判孤立，也不要把「其实还在用」的文件划进去。

## 3. 4.x 附件的命名规则（实测确认）

| 磁盘位置 | 文件名是什么 | 库里的标识 |
|---|---|---|
| `msg/attach/<会话md5>/<YYYY-MM>/Img/<id>[_t\|_h\|_W].dat` | **图片 id** | `Msg_*.packed_info_data` 里的 32hex |
| `msg/video/<YYYY-MM>/<id>.mp4`（+ 同名 `.jpg` 封面） | **视频 id** | `Msg_*.packed_info_data`（基础类型 43）里的 32hex |
| `msg/file/<YYYY-MM>/<名字>` | 原始文件名，**或** `<内容md5>.<ext>` | `message_resource.db` 的 packed_info + appmsg XML 的 `<title>`/`<md5>` |
| `msg/migrate/{File,Video}/<YYYY-MM>/<名字>` | 原始文件名 / `<32hex>`；**可以带 `(N)` 后缀**（见下面第 4 条） | 同上 |
| `msg/attach/<会话md5>/<YYYY-MM>/Rec/<16hex>/{Img,F,V}/**` | 原名 / 图片 id | 同上（**「聊天文件」视图自己的副本目录**） |

**四条独立验证**：

1. **硬链接账本可信**：`hardlink.db` 的 `md5` 列就是**内容 md5**；按 `dir1`→月份拼出的
   `msg/file/<月>/<名>` 路径，抽 200 条，**(大小, md5) 200/200 逐字节吻合**（实测确认）。
2. **图片名 ≠ 内容 md5**：从 `packed_info_data` 解出的 32hex，抽 40 个，**40/40 能在
   `msg/attach/**/Img/` 找到同名 `.dat`**；而这些 `.dat` **解开后的内容 md5 与文件名不符**
   （实测 2/2 不一致）⇒ **文件名是「图片 id」，本地那份是被客户端重编码过的**。
   这是最容易搞错的一点。
3. **消息正文是 zstd**：`WCDB_CT_message_content = 4` 时 `message_content` 是 zstd 帧
   （magic `28 b5 2f fd`），解出来是 appmsg XML，里面有 `<title>` / `<md5>` / `<totallen>`。
4. **`msg/migrate/Video` 的叶子名带 `(N)`，而且同一个月目录里会「同 base 多文件」**
   （实测确认：`<hex>.mp4`、`<hex>(1).mp4`、`<hex>(2).mp4` … 共处同一个月）。
   ⇒ **不要假设那个 32hex 在一个月份目录内唯一**；按名字去重的工具先想清楚这一层。
   对照：`msg/video/<YYYY-MM>/` 是**裸 `<hex>.mp4`**（不含 `(N)`）—— 两者命名习惯不同。
   **这些 `(N)` 来自源命名，不是迁移当天去重重命名的产物**：两个账号里它们的 mtime
   **没有一个**落在迁移当天（实测确认）；「因此来自源命名」这一步是**推断**，
   前提是"被重命名的文件会更新 mtime"。

### 容器形态（实测确认）

本机上 4.x 附件有四种落盘形态：

| 形态 | 说明 |
|---|---|
| 单字节 **XOR `0xA0`** | 解出来就是真 JPEG/PNG/GIF（实测：头 `5f 78 5f 40` → `ff d8 ff e0`，尾 `ff d9` 完整） |
| `\x07\x08V2\x08\x07` 容器 | **不是"未知格式"**：图片头一段 AES-128-ECB、中间一段**明文**、尾段单字节 XOR `0xA0`。结构见 §6.1 |
| 明文 | PDF / ZIP / Office / DWG… |
| 其余高熵 | 例如 4.x 表情库（那是**另一套装法**：分组密码流，明文是 `wxgf`；见 §6.4） |

所以清单里每个文件算**两个哈希**：`md5_raw`（落盘字节）与 `md5_norm`（解开容器后的内容）。
「同一张图存了明文 + 加密两份」会在 `md5_norm` 上合并。

## 4. 重复：**必须按 inode 算，不能按文件个数算**

### 4.1 一个会让人高估一倍的坑（实测确认）

第一版按「冗余文件数 × 大小」算出 **35.98 GB**。抽查发现：**客户端自己已经做了硬链接** ——
同一组 6 个文件**共享同一个 inode、`st_nlink = 6`**，删任何一个都**不省空间**。

改成「**不同 inode 个数 − 1**」之后才是真实可回收量：

| 口径 | 组数 | 冗余文件 | 可回收 |
|---|---:|---:|---:|
| 精确（落盘字节相同） | 9,525 | 17,260 | 24.22 GB |
| 规范化（解开容器后相同） | **9,533** | **17,269** | **24.22 GB** |
| 其中「同内容、不同封装」 | 9 | 10 | ≈ 0 |

其中 **2,576 组已经全部硬链接**（这些组的可回收 = **0**）。

> **结论（实测确认）**：说「重复 36 GB」是**高估**；可回收量是 **24.2 GB**。
> 检查方法：比对 `st_ino` 是否相同，而不是数文件个数。

### 4.2 重复的分布特征（实测确认）

* **`msg/attach` 占绝大多数组**：「同一张图在多个会话目录里各存一份」是最大重复源；
  最大的单组是 **1 张图被 254 个会话各存一份**（≈ 1.4 GB）。
* **`msg/migrate` ↔ `msg/file` 大量重叠**：`msg/migrate` 是迁移的**暂存区**，
  和 `msg/file` / `msg/video` 有近千组同内容（另有数百组只在 migrate 内部重复）。
* **跨封装重复极少**（只有 9 组）⇒ 这套目录里「加密一份 + 明文一份」的情况基本不存在，
  重复主要是**同一份东西被拷了很多遍**。

## 5. 孤立：分三类，风险完全不同

范围内孤立文件按「有没有备份」分三类：

| 类别 | 含义 | 处理风险 |
|---|---|---|
| **A** | 同内容在别处**有索引** | **最低**。删掉不减少任何「库里还认得」的内容 |
| **B** | 只跟**其它孤立文件**重复 | 中。内容至少有第二份，但两份都没有库线索 |
| **C** | **完全独一份** | 最高。库里一点线索都没有，只能靠人判断 |

### 5.1 成因（推断，有结构证据）

* **`msg/migrate`** 是 2.x → 3.x → 4.x 迁移的**暂存区**，4.x 真正读的是 `msg/file` / `msg/video`。
  ⇒ 推断其中大部分是中间副本。**但没实测过删掉客户端会不会出问题。**
* **`msg/attach/**/Rec/**`** 是「聊天文件」视图自己的**二次拷贝**；
  真正的图片目录 `Img/` 里孤立比例**不到 0.4%** ⇒ 真正的图片附件几乎全部有索引。
* **`cache/**`** 是**渲染缓存**（缩略图、气泡图、HTTP 缓存、文件传输临时件），
  按定义就是「可再生」的；里面可能躺着**未完成传输的残留**。
* **`business/emoticon`** 的残余：表情库自己的 `emoticon.db` 都没登记它们。

### 5.2 怎么证明「真的孤立」

怕把「其实有索引、只是没认出来」误判成孤立，做了一次**反向检查**：

1. 把所有已解密的库**当成字节流**，正则捞出**库文件里出现过的全部 32hex**；
2. 从三个区域**各随机抽 300 个孤立文件**，逐个查：
   文件名、文件名里的 32hex、**以及内容 md5（原始 + 规范化）**是否命中库字节流；
3. 结果：**900/900 全部 0 命中**。⇒ 这些文件在库视图里**确实没有任何痕迹**（实测确认，否定结论）。

## 6. 方法本身的边界（未验证）

| 项 | 状态 |
|---|---|
| `\x07\x08V2\x08\x07` 容器 | **格式已知，结构已在本机逐字节验证**（详见 §6.1）。上一版本文写它是未知格式 —— 那**是错的**，错在**没去翻上游代码**，见 §6.2 |
| 未登录账号的库 | **读不了**；它们的「孤立」只是**没查**，不是结论 |
| WAL | 4.x 的 `-wal` 帧头 salt 与 WAL 头部对不上，**无法判定哪一代是当前的**；实测主库与合并结果**行数、时间戳完全一致** ⇒ 合并无收益，本轮不合并 |
| 「孤立」的语义 | =「**我们读得到的库里**没有线索」。不保证客户端不会用到（例如它可能按路径规则去猜） |

### 6.1 V2 容器的真实结构（**实测确认**）

```
[6B  魔数  07 08 'V' '2' 08 07]
[4B  aes_size  小端]
[4B  xor_size  小端]
[1B  flag = 1]
[align16(aes_size) 字节  AES-128-ECB（PKCS7）]   ← 图片**头部**（SOI/DQT/SOF/DHT/SOS）
[raw_len 字节        **明文**，直接就是图片数据]   ← 只有大文件才有这一段
[xor_size 字节       单字节 XOR]
```

| 验证项 | 结果 |
|---|---|
| `15 + align16(aes_size) + raw_len + xor_size == 文件大小` | **23,508 / 23,508 全部成立** |
| 本机 `aes_size` 取值 | **1024**（23,490 / 23,508），对齐后 1040 |
| `xor_size` 上限 | 恰好 **1 MiB**（813 个文件打满）；只有这些文件有 `raw` 中段 |
| **尾段 XOR 密钥** | **`0xA0`** —— 和我们早就在用的单字节容器**同一个键**（上游文档写"通常 0xED"，那是他们的版本） |
| `raw` 中段是不是明文 | **是**。单文件实测：5,437,778 字节的 `raw` 段**原样** 100.00% 合规于 JPEG 熵编码规则（`FF` 后只能是 `00` 或 `D0–D7`；随机字节的期望值约 3.5%） |
| 尾段是不是真数据 | **是**。XOR `0xA0` 后 **99.99%** 合规 |

**字节构成**（全部 23,508 个 / 4,447 MB）：

| 段 | 字节 | 占比 | 要不要密钥 |
|---|---:|---:|---|
| AES 头段 | 23.31 MB | **0.52%** | **要**（客户端运行期持有的 16 字节） |
| raw 中段 | 2,089.77 MB | 46.99% | 不要（明文） |
| XOR 尾段 | 2,333.98 MB | 52.48% | 不要（XOR `0xA0`） |

⇒ **99.48% 的字节不需要任何密钥就能读出来**；剩下 0.52% 就 1040 字节，
但它在**每个文件的开头**、是图片头 ⇒ **没有它，图还是渲染不出来**。
那 16 字节由客户端在运行期持有 —— **本仓库不涉及它的取得方式**。

### 6.2 上一版为什么判断错了（**已证伪，留档**）

| 我上一版写的 | 实际 | 错在哪 |
|---|---|---|
| 「`\x07\x08V2\x08\x07` 格式**未知**；试过固定密钥 AES-ECB/CBC、多种偏移、单字节 XOR 都不出 magic」 | **格式在库里早有完整实现**，我们手里那份 zip 里就带着解码器 | **根本没去翻上游代码**。上一轮我只用了该库的一小部分，**没注意它还有解码实现与格式笔记** |
| 试的那些组合 | 本来就全都错 | ① 密文从**第 15 字节**开始，不是 6/16/22；② 头段用的是**客户端运行期持有的那 16 字节**，不是 V1 的固定值；③ 我对**整个文件**做 XOR，而只有**尾段**是 XOR（中间那段还是明文） |

> **教训**：拿到一个第三方仓库时，**先把它的文件树列全再动手**。
> 「我只用了其中一部分」不等于「其余部分没用」—— 这次白白重造了一遍轮子，还得到了一个错的结论。

### 6.3 这些 V2 是什么时候的（**决策关键**）

| 时间 | 个数 | 体积 | 占比 |
|---|---:|---:|---:|
| 最近一年 | 17,952 | 3,664.84 MB | 82.4% |
| 前一年 | 3,668 | 634.42 MB | 14.3% |
| 无月份标记 | 1,886 | 148.11 MB | 3.3% |
| 更早 | 2 | 0.02 MB | ~0 |
| **十年前那批** | **0** | **0** | **0** |

⇒ **V2 容器与十年前那批恢复出来的历史毫无关系**（那是新版本才引入的形态）。
全部体量 **23,508 个 / 4.34 GB**，占整棵树 208 GB 的 **2.1%**。

### 6.4 表情库是**另一套**，而且很小（实测确认）

`business/emoticon/**` 与 `cache/<月>/Emoticon/**` **不是** V2 容器：

* **603 + 1,083 个文件，`size % 16 == 0` 全部成立** ⇒ 分组密码流形态；
* 公开的上游实现里记的是 **AES-128-CBC / IV = 密钥 / PKCS7**，明文是 `wxgf`
  （微信自有 HEVC 容器）/ GIF / PNG / JPEG；商店表情包 `PersistStore` 是**整包一条连续流**，
  要整包解开后按 `emoticon.db` 的偏移切片；
* **本仓库不涉及这套密钥的取得方式**（同 README 的红线）。
* **体量很小**：`business/emoticon` 只有 **52.6 MB**。

⇒ 表情这一块**不需要**在这份审计里处理；它属于「表情显示」那条线，与附件去重无关。

### 已证伪的旧说法（保留）

| 旧说法 | 实际 | 怎么发现的 |
|---|---|---|
| 用「文件名带 `(N)`」判重就够 | **不完整**：内容级判重能多抓一倍以上；且 `(N)` 里有些**已经硬链接**，删了不省空间 | md5 分组 + 查 inode |
| 重复可回收 ≈ 36 GB | **高估一倍**：2,576 组已硬链接 | `st_nlink` / `st_ino` |
| 资源表的 `data_index` 存文件名 | **只对一部分**：大量是 `'0'`；文件名真正在 `packed_info` 的 protobuf 里 | 逐行解 protobuf |
| `.dat` 文件名 = 内容 md5 | **错**：它是**图片 id**，本地那份被重编码过 | 解开容器算 md5 比对 |

## 7. 第 1 步**已经做了**：硬链接折叠（M1）

> 范围：`<账号>/msg/{attach,file,video,migrate}/**`。**不改路径、不改文件名、不碰任何 `.db`。**

| | 折叠前 | 折叠后 | 变化 |
|---|---:|---:|---:|
| 路径条目（文件数） | 189,187 | 189,187 | **0** |
| 路径条目总字节 | 223,464,432,710 | 223,464,432,710 | **0** |
| 不同 inode | 185,742 | 172,432 | −13,310 |
| **真实物理占用** | **210,838,300,258** | **186,252,310,021** | **−24,585,990,237 (22.897 GB)** |

* 折叠 **13,414 个文件 / 6,687 组**，**0 异常、0 残留**；Windows 侧与 Linux 侧**各独立验一遍**。
* **实际释放量与计划预期逐字节相等**。
* 可逆：撤销日志记录每个文件的 `old_inode / old_size / old_mtime`。

### 7.1 过程中抓到的四个真问题（都可复现、都写进了工具）

| # | 问题 | 结论 |
|---|---|---|
| 1 | **`st_ino` 不能跨平台比** | 同一文件 Linux/drvfs 与 Windows 原生读出的 inode **恒定差 2**（`nlink` 一致）⇒ 工具只信自己现场 stat；plan 与 apply 必须同平台 |
| 2 | **「能省多少」必须按 inode 算** | 同一 inode 上的第 2、3 个名字折叠过来**不省空间**；按文件个数算会把 22.90 GB 高估成 24.94 GB |
| 3 | **「同内容」不等于「同字节」** | 审计按 `md5_norm`（解开容器后）分组，会把「明文 JPEG」与「XOR 加密的 `_W.dat`」归成一组。**硬链接它们 = 把加密容器的字节换成明文 ⇒ 客户端解不出来。** ⇒ 只能折叠 `md5_raw` **逐字节相同**的文件（本轮跳过 9 个） |
| 4 | **Windows READONLY 会让 `os.replace` 报 WinError 5** | 且失败留下的残骸**继承 keeper 的只读属性**，连 `os.remove` 都失败 —— 会被 `except OSError: pass` 静默吞掉。⇒ 替换前只清**即将被淘汰那个 inode** 的只读位；清理残骸前也要先清 |

**副作用（硬链接固有语义）**：同组共用一个 inode ⇒ **共用一个 mtime 和一套 Windows 只读属性**；
被折叠的 `(N)` 名字继承 **keeper** 的这两项。**内容零变化**（路径条目总字节逐字节相同）。

### 7.2 第 2 步（改库删 `(N)` 名字）：**决定不做**

原本的设想是「只留最干净的文件名 + 把库里的索引引过去」。**放弃**，两条理由：

1. **决定性：微信有「手机聊天记录 → 电脑」的合并功能。**
   它必然以 PC 端**已有的文件名与资源记录**作为输入。篡改
   `message_resource.MessageResourceDetail.packed_info` 里的本地名（`X(1).pdf` → `X.pdf`），
   等于给一个我们**完全无法预测其行为**的组件喂非法输入。风险与收益完全不成比例。
2. 次要：它**不额外省一个字节**（空间收益第 1 步已经全部拿到），
   只影响 **5,698 个文件名（3.0%）** —— 而且 74% 的重复**结构上做不到**
   （`msg/attach/<会话md5>/…` 里的会话、`msg/file/<年-月>/` 里的月份都改不了）。

> 「一个内容只留一个文件名」在**跨会话/跨月份**的重复上是不可能的：
> 路径名本身就是客户端定位文件的方式。能做到的上限是
> **一个物理副本 + N 个路径名** —— 而那就是第 1 步已经交付的东西。

### 7.3 仍然没做

* **A 类孤立文件**（1,213 个 / 2.86 GB）：每一个都能在别处找到**有索引的同内容文件**。独立决策。
* `cache/**` 与 `business/**` 的 209 组 / 0.032 GB：**刻意排除**，客户端会就地改写这些文件。
* 客户端冒烟：**需人工**打开 ≥5 个会话确认。

## 8. 纪律（与 `4x-migration.md` / 项目根 `AGENTS.md` 一致）

**先出 manifest（每个路径 + 回退方法）→ 只增不改 → 客户端干净退出 → 先拿一个目录试点。**

> 但 mtime 已冻结）。所以 `AGENTS.md` 里「等 `-wal` 归零」在 4.x 上**做不到**；
> 判据要换成「**进程消失 + `-wal` mtime 不再变化**」。本轮不碰 `.db`，故不阻塞。
